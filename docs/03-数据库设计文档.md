# 数据库设计文档

## 用途与当前范围

本文档维护 MySQL 业务表、字段、约束和关系的正式设计。需求与领域边界分别见 [项目需求文档](01-项目需求文档.md)和[系统架构设计文档](02-系统架构设计文档.md)；HTTP 请求与响应以 [API.md](API.md) 为准。表结构不直接等同于前端展示模型或 API DTO。

认证所需 `users` 表和 `media_source` 表分别由 [V1__create_users.sql](../backend/src/main/resources/db/migration/V1__create_users.sql) 和 [V2__create_media_source.sql](../backend/src/main/resources/db/migration/V2__create_media_source.sql) 落实；[V3__add_media_source_connection_test_time.sql](../backend/src/main/resources/db/migration/V3__add_media_source_connection_test_time.sql) 补充最近成功连接测试时间；[V4__create_media_scan_root.sql](../backend/src/main/resources/db/migration/V4__create_media_scan_root.sql) 落实扫描根配置。资源和公共 Movie 的物理结构在对应切片补充；执行进度与验证记录见 [PROJECT_STATUS.md](../PROJECT_STATUS.md)。

## ID 生成与使用原则

- 后端新生成的业务 UUID 统一采用 UUIDv7。后续 `users.id`、`media_source.id`、`media_scan_root.id`、`scan_task.id`、`user_movie.id` 等需要后端生成的业务 UUID 遵循同一策略；尚未落地的表和字段在对应切片设计。
- 注册已通过统一 `BusinessIds.next()` 生成标准小写 UUIDv7 文本；业务代码不得散落使用 Java 的 `UUID.randomUUID()` 生成业务 ID。实现采用 RFC 9562 的 48 位毫秒时间戳与 74 位安全随机数布局，不承诺同毫秒内严格递增。
- UUIDv7 的时间有序性仅用于 ID 生成和数据库索引局部性的工程考虑；业务创建时间以 `created_at` 等正式时间字段为准。前端不得依赖 UUID 的版本、时间信息或字符结构推导身份、归属、权限或业务状态；UUID 不替代后端权限校验。
- 当前已落地的 `users.id` 继续使用 `CHAR(36)` 保存 UUID 文本，本阶段不切换为 `BINARY(16)`。

## 1. `users`：应用用户

### 1.1 职责

保存登录身份及账号访问状态。注册成功只新增一条 `users` 记录，不自动创建媒体来源、扫描根、资源、个人片库关系或演示数据。`/api/auth/me` 对外只返回 `id`、`username`、`role`，不得返回下列持久化对象本身。

### 1.2 字段

| 字段 | MySQL 8.4 类型 | 空值 / 默认 | 说明 |
| --- | --- | --- | --- |
| `id` | `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 主键；后端生成 UUIDv7，采用 RFC 9562 定义的标准 UUID 文本形式，并按本项目约定统一使用小写表示，作为稳定且不透明的 User ID；JWT `sub` 引用此值。 |
| `username` | `VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 已规范化的登录名；去除首尾空白、ASCII 大写转小写后符合 `^[a-z0-9_]{3,32}$`。 |
| `password_hash` | `VARCHAR(255) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 带算法标识的安全单向密码散列编码结果；不存明文、可逆密文或单独的原始密码。编码方案须完整支持契约允许的 128 个 Unicode 码点，不得静默截断。 |
| `role` | `VARCHAR(8) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL DEFAULT 'USER'` | 仅 `USER`、`ADMIN`；普通注册只能写入 `USER`，管理员初始化另行设计。 |
| `status` | `VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL DEFAULT 'ACTIVE'` | 仅 `ACTIVE`、`DISABLED`；登录及每次受保护请求读取当前状态。 |
| `created_at` | `DATETIME(3)` | `NOT NULL` | 创建时间；按 UTC 写入。 |
| `updated_at` | `DATETIME(3)` | `NOT NULL` | 最近修改时间；按 UTC 写入，账号状态变更时更新。 |

### 1.3 约束与访问规则

- `PRIMARY KEY (id)`；`UNIQUE (username)` 是规范化用户名的最终并发防线。注册与登录在应用层使用同一规范化规则；唯一冲突转换为 `409 USERNAME_TAKEN`。
- 对 `username` 设置格式 `CHECK`，对 `role` 和 `status` 设置允许值 `CHECK`；应用层仍须先执行 API 输入校验。首版迁移已落实并在本机 MySQL 8.4 验证这些约束。[MySQL 8.4 CHECK 约束文档](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)
- 按 `username` 唯一索引查找登录账号，按 `id` 主键查找 JWT 对应账号并复核状态。当前用例不需要额外的角色或状态索引。
- `role`、`status`、`id` 均由可信后端控制，不能从公开注册请求绑定；`password_hash` 不进入 API 响应、普通日志或前端状态。
- 密码由 Spring Security `PasswordEncoder` / `DelegatingPasswordEncoder` 统一编码和验证。新密码默认使用 `Argon2Password4jPasswordEncoder` 与 Password4j 的 Argon2id：64 MiB 内存（65536 KiB）、3 次迭代、并行度 4、32 字节输出；当前实现生成 64 字节随机盐。保存 `{argon2id}` 标识与 Password4j 生成的 `$argon2id$v=19$m=65536,t=3,p=4$…` PHC 字符串，当前完整编码长度为 171 个 ASCII 字符，现有 `VARCHAR(255)` 足够，无需改动 V1 或新增扩容 migration。实现与参数参考 [Spring Security 7 API](https://docs.spring.io/spring-security/reference/7.0/api/java/org/springframework/security/crypto/password4j/Argon2Password4jPasswordEncoder.html)和 [RFC 9106 参数选择](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)。
- `media_source.user_id` 引用 `users.id`，具体归属与查询规则见第 2 节。公共 Movie 不因用户注册而关联到这个用户。

### 1.4 与已确认接口的对应

| 用例 | 数据库行为 |
| --- | --- |
| 注册 | 校验并规范化用户名，散列完整密码，仅插入 `users`；默认角色和状态分别为 `USER`、`ACTIVE`。 |
| 登录 | 用规范化用户名查找，验证密码散列和当前状态；失败不签发 JWT。 |
| 获取当前用户 | 由已验证 JWT 的 `sub` 查找 `id`，复核状态，仅映射公开的 `CurrentUser` 字段。 |

建表迁移不创建账号数据；注册持久化已实现，`created_at` / `updated_at` 在插入时以 `UTC_TIMESTAMP(3)` 写入。登录和每次受保护请求均读取当前账号状态。

## 2. `media_source`：媒体来源

本表保存用户拥有的一套 WebDAV 连接，不保存扫描目录。当前支持首次新增、配置加密保存与本人列表；Vue Mock 展示字段不直接决定数据库字段或 API DTO。

### 2.1 字段

| 字段 | MySQL 8.4 类型 | 空值 / 默认 | 说明 |
| --- | --- | --- | --- |
| `id` | `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 主键；后端生成小写标准 UUIDv7 文本。 |
| `user_id` | `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 归属用户，引用 `users.id`，由可信 CurrentUser 填入；每条来源只属于一个用户，同一用户可拥有多条来源（`user_id` 非唯一）。 |
| `name` | `VARCHAR(80)` | `NOT NULL` | 用户自定来源名称；保存前去除首尾空白，不允许空名称。 |
| `source_type` | `VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL DEFAULT 'WEBDAV'` | P0 仅允许 `WEBDAV`；不按 AList、NAS、Nextcloud 拆分类型。 |
| `connection_config_ciphertext` | `BLOB` | `NOT NULL` | 使用应用主密钥保护的完整 WebDAV 连接配置，包含地址及所需认证信息；无凭据的连接也保存加密配置，不存明文密码或 Token。 |
| `enabled` | `TINYINT(1)` | `NOT NULL DEFAULT 1` | 来源启用状态；`1` 为启用，`0` 为停用。 |
| `last_connection_test_at` | `DATETIME(3)` | `NULL` | 保存前最近成功连接测试的 UTC 时间；V3 新增，既有未测试记录为空。不表示当前在线。 |
| `created_at` | `DATETIME(3)` | `NOT NULL` | 创建时间；按 UTC 写入。 |
| `updated_at` | `DATETIME(3)` | `NOT NULL` | 最近修改时间；按 UTC 写入。 |

### 2.2 约束与本人查询

- `PRIMARY KEY (id)`；`FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE RESTRICT`。每条来源必须且只能归属一个现存用户；P0 不删除用户，未来删除账号前须另行处理其来源，不由外键静默级联删除。
- 建立 `INDEX idx_media_source_user_id (user_id)`，服务本人来源列表查询；`source_type` 仅允许 `WEBDAV`，`enabled` 仅允许 `0` 或 `1`，由数据库 `CHECK` 与应用层校验共同约束。本切片不规定来源名称唯一。
- 新建来源时后端从可信 CurrentUser 填入 `user_id`。本人来源列表按 `WHERE media_source.user_id = :currentUserId` 查询；普通用户和管理员访问此列表均只看本人来源，不能用请求中的 `userId` 扩大范围。
- 查询成功且本人确无来源时才得到空集合；数据库失败或本人损坏密文不能转换为空集合。非空响应 DTO 见 API，不返回持久化对象。
- 完整连接配置使用 AES-256-GCM、随机 nonce 加密；密文带格式版本，认证附加数据绑定 `user_id` 与 `id`，阻止密文跨用户或来源挪用。主密钥 `MEDIA_SOURCE_ENCRYPTION_KEY` 为 32 字节随机数的 Base64，保存在后端安全配置，须与数据库备份一起保护；丢失或直接替换会使既有密文无法读取，当前未实现在线密钥轮换。
- 仅由 Spring Boot 在连接使用或生成脱敏展示信息时解密，密文、凭据和含敏感信息的地址不得进入列表响应或日志。列表只在本人行解密后投影无认证信息的地址；测试中状态、扫描摘要与 MediaScanRoot 不写入本表。测试未保存连接不写数据库；首次新增重新测试后才 INSERT，不自动建扫描根或启动扫描。

V1/V2 保持已执行脚本不变，V3 单独扩展测试时间。本人空/非空列表、来源新增及配置加密已实现；接口边界见 API，实际迁移验证见 PROJECT_STATUS。

## 3. `media_scan_root`：来源扫描范围

本表只保存本人来源下选中的目录，不代表已经扫描、创建资源或加入个人片库。关系为 `users` 1 : N `media_source` 1 : N `media_scan_root`；归属沿来源查询，不另存可被客户端指定的 `user_id`。

### 3.1 字段

| 字段 | MySQL 8.4 类型 | 空值 / 默认 | 说明 |
| --- | --- | --- | --- |
| `id` | `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 主键；后端生成小写标准 UUIDv7 文本。 |
| `source_id` | `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin` | `NOT NULL` | 引用 `media_source.id`；一条扫描根只属于一个来源。 |
| `path` | `VARCHAR(2048) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin` | `NOT NULL` | 已解码、规范化的来源内绝对目录路径，最多 2048 个 Unicode 码点；不是远程 URL。 |
| `path_hash` | `BINARY(32)` | `NOT NULL` | 应用层对规范路径 UTF-8 字节计算的 SHA-256，供完整路径唯一索引使用，不进入 API。 |
| `enabled` | `TINYINT` | `NOT NULL DEFAULT 1` | 扫描根启用状态，`CHECK` 只允许 `0` 或 `1`。新根启用；保留路径沿用既有值。V4 不使用整数显示宽度。 |
| `created_at` | `DATETIME(3)` | `NOT NULL` | 新增时以 `UTC_TIMESTAMP(3)` 写入。 |
| `updated_at` | `DATETIME(3)` | `NOT NULL` | 新增时以 `UTC_TIMESTAMP(3)` 写入；当前整批保存保留路径不改变记录。 |

### 3.2 约束与整批保存

- `PRIMARY KEY (id)`；`FOREIGN KEY (source_id) REFERENCES media_source(id) ON DELETE RESTRICT`。来源仍有扫描根时不能直接删除，避免静默丢失配置；当前未提供来源删除接口。
- `UNIQUE (source_id, path_hash)` 对同来源完整规范路径去重，避免直接索引 2048 字符 utf8mb4 路径超过 InnoDB 索引字节限制；该复合索引同时服务按来源查根。应用层对同一散列对应的不同原文路径报错并回滚，不能因散列相同覆盖另一根。路径比较区分大小写、不去除目录名中的空格、不进行 Unicode 归一化。
- 服务先通过 `media_source.user_id = CurrentUser.id AND media_source.id = sourceId` 核实本人来源，再读扫描根或解密访问 WebDAV；`USER` 与 `ADMIN` 均使用同一本人归属规则。查询结果按 Java 字符串路径自然顺序稳定返回。
- 整批提交包含 0～32 个路径；应用层沿用 `SourceDirectoryPath` 规范化，拒绝重复及祖先/后代重叠（按 `/` 目录边界比较，停用根同样参与），空集合合法清空。所有选中目录均先经有整批截止时间的只读 WebDAV `Depth:0` 验证；任意失败保留旧配置。
- 上游全通过后开启短事务，`SELECT ... FOR UPDATE` 锁定本人来源行，再读取现有根进行替换；并发保存按来源串行提交，读取只能得到一个完整配置。网络期不持锁；锁定后连接密文若与验证前不同则拒绝保存。
- 保留路径保留 `id`、`enabled` 及时间；新增路径创建 UUIDv7 并启用；取消的路径删除。数据库故障整体回滚。保存不修改 `media_source.enabled`、`last_connection_test_at` 或连接配置，也不创建扫描任务、媒体资源及个人片库关系。
