## 1. 文档目的

本文档用于固化项目第一版的产品目标、功能范围、优先级、业务规则、AI能力、非功能要求和验收标准，作为后续设计、开发、测试和毕业答辩共同遵循的需求基线。

本文档的主要作用如下：

1. 防止项目在开发过程中演变为播放器、视频网站、资源存储平台或企业媒体系统。
2. 明确传统业务系统、大语言模型、RAG、Agent和外部播放器之间的职责边界。
3. 确保第一版优先完成可运行、可演示的完整产品闭环。
4. 为后续架构设计和功能验收提供可追踪的依据。

### 1.1 基线原则

- 第一版以电影为核心，电影管理和使用流程必须完整跑通。
- 产品主体为Web系统，不开发桌面客户端、移动端客户端或内嵌播放器。
- 系统只管理影视资源信息，不保存影视视频文件本身。
- 平台不提供、聚合或分发任何公共可播放影视资源；新用户片库默认为空，只管理用户自行接入的媒体来源。系统中可预先存在供全体用户复用的公共Movie元数据，但这不代表任何用户拥有对应影片，也不会使影片自动进入其个人片库。
- AI必须嵌入真实影音业务，不得退化为无业务依据的通用聊天机器人。
- AI推荐必须优先来自用户真实拥有且当前可访问的个人片库。
- Spring Boot是核心业务事实的唯一来源，AI服务不维护第二套业务真相。
- 系统采用“弱后台、强个人端”的产品结构：个人影音业务始终是主体，P0仅增加账号状态、聚合统计、运行监控和审计查询等轻量系统管理能力。
- 内容运营管理员与系统管理员必须区分：本项目不设置影视内容运营管理员，但设置应用内部系统管理员`ADMIN`；部署维护者仍是运行环境角色，不等同于产品权限角色。
- 当功能广度、AI技术深度和闭环完整度发生冲突时，优先保证P0业务闭环。

### 1.2 本次需求收敛结论

已确认产品决策之间不存在需要重新讨论的直接冲突。第一版产品定位为类似Infuse的“个人影音资源管理与AI辅助工具”，平台本身不提供任何公共可播放影视资源。系统开放用户自主注册和登录；注册或登录后的默认片库为空，只有用户自行添加WebDAV媒体来源并拥有本人可访问的MediaResource、建立其与Movie的关系后，该Movie才进入当前用户的个人片库。

Movie表达所有用户可复用的影片客观元数据，而不是平台提供的影视资源。公共Movie记录可以由其他用户此前的首次建档流程创建，也可以在未来由管理员预建，但它不会自动关联新用户，不包含公共MediaResource，也不会改变新用户没有MediaSource、MediaResource和个人片库关系的初始状态。

第一版P0网络媒体来源统一收敛为WebDAV，核心只实现`WebDavMediaSourceAdapter`。AList、NAS WebDAV和Nextcloud处于同一Provider层级，均不形成独立MediaSource类型。统一`MediaSource`/`MediaSourceAdapter`抽象继续保留，以便未来扩展FileSystem、SMB或其他来源，但`FileSystemMediaSourceAdapter`、本地硬盘、仅局域网可达NAS和Local Agent均不属于本科毕设第一版P0。

此前“由服务端Spring Boot直接启动mpv进程”的方案与Web系统可部署于Linux、NAS或服务器的目标冲突，现已废止。第一版正式播放链路统一为浏览器通过自定义`mpv://`协议调用用户Windows本机的mpv；平台只负责控制面和播放定位生成，媒体数据尽量从用户WebDAV来源直接流向mpv。

此前“完全不设置产品管理员端”的结论调整为：第一版在同一个Vue Web应用中增加受`ADMIN`保护的轻量系统管理中心，用于系统概览、普通用户账号启停、任务与AI调用监控、脱敏审计查询、系统健康和只读配置摘要。该管理端不管理影视内容、不代替用户维护个人片库、不提供复杂RBAC，也不改变个人数据隔离和“弱后台、强个人端”定位。

## 2. 项目背景

个人用户的影视资源通常分散在本地磁盘、NAS和网盘中。随着片库增长，用户会面临文件命名混乱、影片信息缺失、资源版本重复、来源难以统一管理、传统搜索表达能力不足以及“资源很多但不知道看什么”等问题。

成熟的个人媒体中心产品已经验证了个人影视资源统一管理、元数据整理、多来源访问和高质量播放等场景的实际需求。本项目不重新开发播放器，也不复制完整的媒体服务器能力，而是在用户已有资源和成熟播放器之间增加一层智能管理与决策系统：统一组织个人片库，通过TMDB官方API完成电影识别与事实元数据刮削，通过ffprobe补充实际文件技术信息，通过大语言模型理解自然语言需求，通过RAG约束回答依据，通过Agent执行跨片库、观看历史和资源状态的复合查询，最后调用mpv完成高质量播放。

已验证的关键可行链路为：

> 网盘资源 → AList等WebDAV Provider → WebDAV → 当前可用播放定位 → `mpv://`自定义协议 → Windows本机mpv → 高质量播放

上述验证为第一版的播放方案提供了现实基础，但不把AList建模为独立MediaSource类型，也不预设所有WebDAV服务都具有相同的播放URL和认证行为。

## 3. 项目定位

### 3.1 产品定义

本项目是一套面向个人用户的AI增强型影音平台，用于统一管理用户已有的电影资源，并帮助用户完成“资源整理—影片查找—内容理解—观影决策—外部播放”的完整流程。

### 3.2 核心价值主张

系统主要回答以下问题：

1. 我的片库中实际有哪些电影，它们位于哪里？
2. 我能否用自然语言找到符合当前需求的影片？
3. 在我真实拥有且可以访问的资源中，现在看什么最合适？
4. 这部影片讲什么、风格如何、是否适合我，相关回答有什么依据？
5. 我选择的具体资源版本能否通过本机mpv播放？

### 3.3 产品原则

- **个人工具优先**：围绕个人片库、个人偏好和个人观看历史设计。
- **片库事实优先**：影片、媒体资源、来源和观看状态以业务系统中的真实数据为准。
- **可访问资源优先**：搜索和推荐不仅判断“是否拥有”，还要考虑资源当前是否可访问。
- **可靠信息优先**：P0的演员、导演、年份、Movie.runtime和外部客观评分等影片事实来自TMDB官方API。
- **P0数据源明确**：影片事实来自TMDB官方API，实际文件技术事实来自MediaSource与ffprobe，AI语义信息来自LLM，三类信息不得互相覆盖。
- **AI解释而非编造**：LLM用于理解、总结、推理、语义标签和推荐解释，不生成事实性元数据。
- **播放能力解耦**：平台负责资源管理和播放入口，mpv负责解码、HDR、音频和字幕播放。
- **中文体验优先**：在数据源允许的情况下优先展示中文片名、中文简介和中文海报。

## 4. 项目目标

### 4.1 第一版业务目标

1. 支持用户自主注册和登录；新用户默认空片库，并可添加自己的WebDAV媒体来源。AList、NAS WebDAV和Nextcloud等服务均作为WebDAV Provider接入。
2. 支持扫描电影文件、识别影片、刮削可靠元数据并建立个人电影片库。
3. 支持同一影片关联多个独立媒体资源版本，并允许用户播放前选择版本。
4. 支持片库浏览、传统搜索、收藏、标签、观看状态和基础播放记录。
5. 支持针对真实片库的自然语言搜索和可解释推荐。
6. 支持基于RAG的影片助手，默认无剧透并以检索资料约束回答。
7. 至少实现一个具有真实工具调用和多步骤执行过程的LangGraph Agent任务。
8. 支持获得当前有效播放地址，并通过`mpv://`调用Windows本机mpv。
9. 使用Spring Security + JWT建立可信登录身份，并保证用户数据、媒体来源、资源和AI上下文相互隔离。
10. 记录关键用户业务操作，并完成AI搜索、推荐、RAG和Agent的论文实验与验收评价。
11. 提供轻量系统管理中心，使系统管理员能够了解聚合使用情况、普通用户账号状态、后台任务、AI运行状态、脱敏审计记录和核心依赖健康状态。
12. 建立可通过`request_id`和`task_id`定位问题、且与业务审计记录分离的基础可观察性。
13. 形成可部署、可运行、可演示的P0完整闭环。
14. 将已选定的TMDB主Poster和主Backdrop长期保存到自有OSS，使已刮削片库的日常浏览不依赖TMDB图片服务实时可用。

### 4.2 AI目标

- 将用户口语化的观影需求转化为可执行的片库查询条件。
- 对情绪、节奏、氛围等传统字段难以覆盖的要求进行语义匹配。
- 结合片库事实、观看历史和资源状态生成有限、可解释的候选结果。
- 通过RAG降低影片问答和推荐中的模型幻觉。
- 通过Agent编排真实业务查询与资源检查，而不是直接输出模型记忆中的答案。

### 4.3 第一版成功标志

当普通用户能够从自主注册/登录后的空片库开始，添加自己的WebDAV来源，并完成连接测试、扫描、识别、刮削、浏览、自然语言选片、AI影片问答、选择资源版本、通过mpv播放和查看播放记录的全过程；同时系统管理员能够通过轻量管理中心完成账号状态管理、聚合监控、脱敏审计和健康查看时，第一版产品成立。管理端是辅助验收项，不得压过个人影音主流程。

## 5. 目标用户

### 5.1 核心用户

拥有一定规模个人电影资源，并希望改善资源整理、查找、理解和选片体验的个人影音用户。

典型特征包括：

- 电影存放在可通过WebDAV访问的NAS、网盘或远程存储中。
- 使用AList、NAS WebDAV、Nextcloud等Provider把自有存储以WebDAV形式接入。
- 使用Windows电脑和mpv进行高质量播放。
- 重视4K、HDR、高码率音视频和字幕播放效果，但不希望平台重新实现播放器。
- 片库从数十部到数千部不等，存在多个版本、来源分散或命名不规范的问题。
- 经常需要按情绪、时长、观看场景等模糊条件选择影片。

### 5.2 次要用户

- 刚开始整理个人数字片库的普通用户。
- 在家庭内部使用同一NAS或WebDAV服务，但希望保留个人来源、片库、收藏和观看历史的用户。
- 希望借助AI快速理解影片背景、主题或系列关系的用户。

### 5.3 辅助角色

- **系统管理员**：应用系统内部的`ADMIN`角色，负责普通用户账号状态、聚合统计、任务与AI运行监控、脱敏审计查询和系统健康查看，不参与用户个人片库内容运营。
- **部署维护者**：负责服务器、Docker、配置文件、环境变量、备份、原始技术日志和mpv部署指导的运行环境角色，不天然拥有应用内`ADMIN`权限。
- 实际部署中同一个人可以同时承担系统管理员与部署维护者，但两者的授权来源、职责和操作入口必须保持概念分离。

### 5.4 非目标用户

- 企业影视资产管理者。
- 学校教学资源管理者。
- 商业视频网站运营者。
- 需要影视内容审核、版权审核或内容运营后台的运营人员。
- 需要公开视频上传、转码、分发、付费和版权运营的用户。
- 需要企业级租户体系、组织部门或复杂权限管理的机构。

## 6. 核心用户痛点

| 痛点 | 用户表现 | 系统应提供的价值 |
| --- | --- | --- |
| 资源分散 | 不清楚电影位于哪个WebDAV Provider或远程目录 | 统一来源管理和个人片库 |
| 文件混乱 | 文件名不规范、影片难以识别 | 扫描、识别、刮削和人工修正 |
| 版本重复 | 同一电影存在多个清晰度和来源 | 逻辑影片与媒体资源版本分离管理 |
| 搜索困难 | 只能记住模糊剧情、风格或观看需求 | 传统检索与自然语言语义检索结合 |
| 选择困难 | 片库很多但不知道现在看什么 | 基于片库、历史和即时需求的解释型推荐 |
| 内容理解成本高 | 不知道影片背景、风格或系列关系 | 有依据、可控制剧透的AI影片助手 |
| 远程定位可能失效 | 远程媒体播放定位可能具有认证、重定向、临时性或时效性，历史定位可能失效 | 播放前检查资源状态并解析当前PlaybackLocator |
| 播放环境割裂 | Web系统与Windows本地播放器分离 | 通过`mpv://`建立明确播放入口 |

## 7. 用户角色

第一版角色模型收敛为未登录访问者、普通用户`USER`、系统管理员`ADMIN`和部署维护者。`USER`与`ADMIN`是Spring Security管理的应用内部认证/授权角色；部署维护者是运行环境角色。系统仅采用`USER/ADMIN`两级角色，不建设permission表级权限体系、多级管理员、菜单权限树、部门、租户、`USER_ROLE`或`ROLE_PERMISSION`等企业级复杂RBAC。不同普通用户之间仍必须按照CurrentUser严格隔离媒体来源、MediaResource可见范围、个人片库、收藏、观看状态、播放历史、AI/RAG数据和会话等用户数据。

### 7.1 未登录访问者

- 可以访问注册和登录入口。
- 不得查看个人片库、来源配置、播放地址、观看记录或AI对话内容。

### 7.2 普通用户 USER

- 管理本人可见的媒体来源和片库。
- 浏览、搜索、收藏和标记影片状态。
- 使用自然语言搜索、推荐、影片助手和Agent。
- 选择媒体资源版本并发起播放。
- 查看个人播放记录和偏好设置。
- 只能查看本人的OperationRecord，不得访问管理端或任何跨用户聚合能力。

### 7.3 系统管理员 ADMIN

- 通过应用登录进入同一Vue Web应用中的受保护管理区域。
- 查看系统级聚合指标、普通用户基础账号信息、扫描/索引任务、AI调用运行摘要、系统级脱敏OperationRecord以及系统健康与只读配置摘要。
- 启用或禁用普通用户账号；这类状态变更必须形成标明`ADMIN` actor的管理员审计记录。
- 默认不得查看或修改用户私人观影明细、MediaSource凭据、完整文件路径、PlaybackLocator、完整AI Prompt或私人对话，也不得冒充用户。
- 不承担影视内容审核、片库运营或替用户维护个人数据的职责。

新注册用户默认且只能获得`USER`。`ADMIN`不得通过普通注册流程获得；P0不提供用户自行升级、也不提供管理员任意向其他用户授予`ADMIN`的产品功能。管理员账号的初始化方式留给后续安全与部署详细设计。

### 7.4 部署维护者

部署维护者负责服务器、Docker、配置文件、环境变量、备份、原始结构化技术日志和外部依赖运维，并指导Windows客户端安装mpv及注册自定义协议。该角色属于运行环境维护角色，不等同于`ADMIN`，也不以“数据库管理员身份”形成产品功能。

系统开放用户自主注册和登录。部署维护者不负责为普通用户预置片库；任何新用户首次进入系统时均看到空片库。

## 8. 产品使用场景

### 8.1 首次建立片库

1. 用户自主注册或登录系统，首次进入时看到空片库，并添加一个本人拥有访问权的WebDAV媒体来源及目录范围。
2. 系统测试来源是否可连接，并提示测试结果。
3. 用户启动扫描，系统展示扫描进度和阶段结果。
4. 系统发现视频文件，由媒体来源取得文件名、相对路径、大小、修改时间和稳定定位等资源事实。
5. 系统确定性解析原始文件名和目录名：先提取并保留可能存在的Edition/Cut标签，再去除分辨率、编码、音频、发行组等命名噪声，最后使用片名与年份调用TMDB电影搜索。
6. 系统根据标题、年份、原始标题和候选唯一性计算匹配置信度；确认TMDB Movie ID后先复用已经存在的公共Movie，不存在时才取得中文优先的P0影片元数据并完成统一公共Movie建档。
7. 系统对WebDAV远程媒体按best-effort执行ffprobe探测；探测失败、超时或被跳过均不阻塞MediaResource入库和TMDB刮削，无法确定的技术字段保持UNKNOWN或空。
8. 高置信度结果自动进入片库，低置信度或多候选结果进入待确认列表，无候选资源保留为未识别MediaResource。
9. 用户修正必要的匹配结果后，得到统一电影片库。

### 8.2 管理同一影片的多个版本

用户在电影详情页看到该电影关联的一个或多个WebDAV媒体资源版本。每个版本独立展示Provider/来源、可访问状态、可识别的媒体特征，以及文件名或目录名能够明确识别时的Edition/Cut标签。例如《银翼杀手》的Final Cut、Theatrical Cut和Director's Cut仍属于同一个Movie，只是不同MediaResource，用户可以选择其中一个播放。

### 8.3 使用自然语言寻找影片

用户输入：

> 找一部片库里没看过的科幻片，两个小时以内，不要太压抑。

系统识别“个人片库、未看、科幻、120分钟以内、低压抑程度”等约束，组合结构化查询和必要的语义检索，只返回用户真实拥有的候选影片，并解释匹配原因。

### 8.4 获取个性化选片建议

用户输入：

> 今天有点累，想看一部轻松一些、时间不要太长的电影。

系统结合用户片库、观看状态、历史摘要、语义标签和资源可访问性，给出少量候选影片。推荐结果包含理由、Movie标准时长、观看状态和可用资源概况。

### 8.5 使用影片详情页AI助手

用户进入某部电影详情页并询问：

> 不要剧透，告诉我这部影片的风格以及观看前需要了解什么。

助手基于该影片元数据、简介、演职员资料和语义标签回答。若用户询问结局，系统必须先取得用户对剧透模式的明确许可。

### 8.6 Agent执行复合选片任务

用户输入：

> 帮我找三部片库里没看过、两个小时以内、不要太压抑的科幻片，并检查资源当前是否可播放。

Agent理解条件，查询真实片库和观看历史，进行结构化筛选与必要的语义检索，查询候选影片的所有资源版本，检查状态并排序，最终返回三部或如实说明不足三部。

### 8.7 调用本机mpv播放

1. 用户在电影详情页选择具体媒体资源版本。
2. 系统获取或确认该资源当前可用的播放路径或URL。
3. 对WebDAV资源，系统在播放时检查当前资源状态并解析本次PlaybackLocator；具体认证、Header、重定向或临时URL行为由播放Technical Spike验证。
4. 浏览器调用经过正确编码的`mpv://`链接。
5. Windows提示用户确认首次外部协议调用，并由已注册协议启动本机mpv。
6. mpv直接读取该媒体资源，系统记录本次播放启动行为。
7. 若本机未安装mpv或未注册协议，系统提供明确说明和复制播放地址的替代操作。

### 8.8 轻量系统管理与排障

1. 系统管理员以`ADMIN`身份登录同一个Vue Web应用并进入受保护的管理区域。
2. 管理员查看注册用户、近期活跃用户、MediaSource、MediaResource、入库规模、扫描任务和AI调用的聚合摘要及简单趋势。
3. 管理员查询某个普通用户的基础账号状态与聚合使用统计，并在必要时启用或禁用该账号。
4. 管理员通过`task_id`查看扫描/索引任务阶段、结果数量、耗时、错误类别与降级状态，通过`request_id`关联AI调用和近期异常摘要。
5. 管理员查看一条不含敏感载荷的系统级OperationRecord和核心依赖健康状态；原始Spring Boot/FastAPI技术日志仍由部署维护者在服务端排障。

该场景回答“系统是否正常、任务为何失败、谁进行了关键操作”，而不是让管理员查看或运营用户具体影片、收藏、观看历史和私人AI内容。

### 9.4 系统职责约束

- Vue Web前端是第一版的主要用户交互入口，负责呈现片库、AI结果、资源版本和外部播放操作。
- 管理端不建立第二套Vue工程；同一Vue应用只向`ADMIN`展示轻量管理区域，路由隐藏仅改善体验，不能代替Spring Security授权。
- Spring Boot业务后端是用户、影片、媒体资源、来源、收藏、标签、观看状态和播放记录的唯一业务事实来源。
- Spring Boot中的明确Admin Application Service负责跨模块管理查询与编排；管理员请求必须先验证`ADMIN`，不得把普通业务接口改造成接收任意`userId`的跨用户接口。
- FastAPI AI服务负责LLM、Embedding、RAG、Agent和AI结构化输出，不得维护与Spring Boot并行的第二套业务真相。
- FastAPI需要业务事实时，必须从Spring Boot提供的受控业务能力中取得当前数据；具体调用方式为【待后续系统设计阶段确定】。
- AI索引是检索辅助数据，不得取代核心业务数据，也不得以索引中的旧状态覆盖当前业务事实。

## 11. 详细功能需求

### 11.1 用户与个人设置

- **FR-USER-001**：系统应支持用户自主注册，并使用Spring Security + JWT完成第一版登录认证；登录成功后由Spring Boot签发JWT，Vue后续请求使用`Authorization: Bearer <JWT>`携带登录身份。
- **FR-USER-002**：系统应支持用户维护基本个人设置。
- **FR-USER-003**：系统应为不同用户分别保存收藏、偏好、观看状态和播放记录。
- **FR-USER-004**：系统应支持用户退出登录。
- **FR-USER-005**：系统内部仅采用`USER/ADMIN`两级角色，不建设企业级租户体系、组织部门、permission表级权限、多级管理员或复杂RBAC；普通用户之间仍必须按照CurrentUser执行严格的数据与资源隔离。
- **FR-USER-006**：用户应能查看与AI推荐相关的个人偏好，并能够调整或清除这些偏好。
- **FR-USER-007**：系统只能从已验证JWT建立的可信当前用户上下文识别请求用户，不得信任前端请求体、查询参数或路径中自行声明的`userId`。
- **FR-USER-008**：每个MediaSource必须归属于明确用户；用户不得查看、修改、启停、扫描或取得其他用户来源的凭据。
- **FR-USER-009**：MediaResource通过所属MediaSource进入用户访问范围；按资源ID访问时必须同时校验当前用户是否有权访问，不能只判断对象存在。
- **FR-USER-010**：个人片库视图、收藏、用户标签、观看状态、播放记录、推荐偏好、AI会话和AI用户上下文必须按用户隔离；OperationRecord的普通用户入口同样只能返回本人记录，唯一例外是`ADMIN`通过独立受控审计用例查询系统级脱敏记录。
- **FR-USER-011**：用户不得通过修改MediaSource、MediaResource、Movie、收藏、历史、操作记录或播放相关标识访问超出本人范围的数据。
- **FR-USER-012**：Movie继续表达TMDB确认后的共享逻辑影片事实，不为每个用户复制一份Movie；公共Movie元数据存在本身不等于平台提供公共影视资源，也不等于影片已属于某个用户。Movie只有通过当前用户本人可访问的MediaResource建立片库关系后，才出现在该用户个人片库中。
- **FR-USER-013**：AI搜索、推荐、RAG和Agent必须遵守与普通业务入口相同的用户范围；向量检索必须携带用户范围，但最终权限仍由Spring Boot复核。
- **FR-USER-014**：新注册用户首次登录后的个人片库必须为空，即没有MediaSource、MediaResource、个人片库关系、其他用户资源或平台赠送的可播放影片。系统允许已有公共Movie元数据继续存在和复用，但不得因此为新用户建立资源或片库关系；只有当前用户自行添加并扫描媒体来源后才建立其片库。
- **FR-USER-015**：新注册用户默认且只能获得`USER`；普通注册流程、个人设置和P0管理端均不得提供自行升级或任意授予`ADMIN`的能力。

### 11.2 资源扫描与导入

- **FR-SCAN-001**：用户应能对已启用媒体来源发起扫描。
- **FR-SCAN-002**：系统应识别常见电影视频文件，并忽略明显不属于媒体主体的无关文件。
- **FR-SCAN-003**：系统应记录媒体文件的位置、来源、文件信息和可识别的资源特征。
- **FR-SCAN-004**：系统应根据文件名和目录信息产生影片识别候选。
- **FR-SCAN-005**：扫描过程应展示当前状态、已发现数量、成功数量、待确认数量和失败数量。
- **FR-SCAN-006**：用户应能查看扫描失败或未识别的原因。
- **FR-SCAN-007**：重复扫描不得无故产生重复的逻辑影片或重复资源记录。
- **FR-SCAN-008**：已不存在或不可访问的文件应被标记，不得静默从用户片库中永久删除。
- **FR-SCAN-009**：系统应允许用户重新扫描指定来源。
- **FR-SCAN-010**：MediaSource应提供文件名、相对路径、ResourceLocator、文件大小、文件修改时间，以及来源支持时的稳定资源ID。
- **FR-SCAN-011**：系统应区分来源直接提供的文件事实、ffprobe探测事实和TMDB影片事实，不得用其中一类数据冒充另一类。
- **FR-SCAN-012**：媒体技术探测失败不得阻止MediaResource被发现、识别或关联Movie。

### 11.3 影片识别与元数据刮削

#### 11.3.1 P0数据源与刮削定义

- **FR-META-001**：P0必须使用TMDB（The Movie Database）官方API作为唯一实际影片元数据来源。
- **FR-META-002**：架构可以保留MovieMetadataProvider抽象，但P0只要求一个TMDBMovieMetadataProvider实际实现，不同时接入IMDb、豆瓣、OMDb、TVDB或其他影视数据库。
- **FR-META-003**：本项目中的“影片刮削”是指根据MediaResource文件名、目录名和年份等候选信息查询TMDB、识别真实电影、取得可靠事实元数据，并建立MediaResource到Movie的关联。
- **FR-META-004**：系统不得抓取影视网页HTML作为P0元数据来源，也不得自行开发电影数据爬虫。
- **FR-META-005**：LLM不是影视数据库，不得根据文件名生成或补齐TMDB事实元数据。

#### 11.3.2 P0影片识别流程

- **FR-MATCH-001**：系统应从媒体文件名和目录名中提取影片名称、年份等候选信息。
- **FR-MATCH-002**：确定性文件名解析应能够识别并去除分辨率、视频编码、音频格式、字幕组、发行组、BDRip、WEB-DL、Remux、HDR和Dolby Vision等常见命名噪声。
- **FR-MATCH-003**：系统应使用解析后的候选片名和年份调用TMDB电影搜索。
- **FR-MATCH-004**：系统应依据标题匹配程度、年份、原始标题和候选唯一性等确定性信息计算匹配置信度。
- **FR-MATCH-005**：高置信度且唯一的候选可自动确认Movie；低置信度或多候选必须由用户人工确认；无候选时应保留未识别MediaResource。
- **FR-MATCH-006**：只有确认TMDB Movie ID后，系统才应获取并保存完整P0影片元数据。
- **FR-MATCH-007**：LLM不得成为自动匹配成功的最终依据，也不得绕过匹配置信度和人工确认建立事实关联。
- **FR-MATCH-008**：未来AI可以解释候选差异，但解释结果不能直接替代用户确认。
- **FR-MATCH-009**：用户应能重新匹配或修正错误结果，人工确认后的关联不应被普通重复扫描自动覆盖。
- **FR-MATCH-010**：系统必须在清理技术与发行噪声之前，从原始文件名和目录名中确定性识别并保留常见Edition/Cut标签，例如Theatrical Cut、Director's Cut、Extended Cut、Final Cut、IMAX、Special Edition、Unrated或Anniversary Edition。
- **FR-MATCH-011**：Edition/Cut标签不是影片匹配噪声，不得在提取并保留其MediaResource语义之前直接删除；Edition提取后再清理噪声、提取片名与年份并执行TMDB匹配。
- **FR-MATCH-012**：确认TMDB Movie ID后，系统应先查询并复用对应公共Movie；已存在时不得重复创建公共Movie、重复取得完整TMDB资料或重复下载和保存相同主Poster/主Backdrop。
- **FR-MATCH-013**：公共Movie不存在时，系统应完成一次统一建档：取得规范化TMDB事实、按系统级固定规则选定一个主Poster和一个主Backdrop、将所需图片持久化后创建公共Movie，再使当前MediaResource关联该Movie。多个用户同时首次建档同一TMDB影片时，最终只能形成一条公共Movie。

#### 11.3.3 P0影片身份与基本资料

- **FR-META-006**：Movie必须保存TMDB Movie ID，作为P0供应商下的外部唯一标识。
- **FR-META-007**：Movie必须支持中文片名和原始片名。
- **FR-META-008**：Movie必须支持上映日期，并能够方便展示和按上映年份搜索；是否单独持久化年份留给数据库设计决定。
- **FR-META-009**：Movie必须支持中文简介；中文简介缺失时可使用TMDB返回的其他可用语言内容降级，但不得让LLM生成内容并冒充TMDB官方简介。
- **FR-META-010**：Movie必须支持TMDB标准影片时长runtime。
- **FR-META-011**：Movie必须支持原始语言。
- **FR-META-012**：Movie必须支持一个或多个制作国家或地区。
- **FR-META-013**：Movie必须支持一个或多个TMDB Genre，并支持按Genre筛选。
- **FR-META-014**：Genre属于TMDB客观分类，不得与AI语义标签合并为同一概念。

#### 11.3.4 导演、主要演员与Person

- **FR-CREDIT-001**：P0应取得影片所有主要Director信息，至少包括TMDB Person ID、姓名，以及数据源存在时的原始姓名。
- **FR-CREDIT-002**：系统应支持按导演搜索影片。
- **FR-CREDIT-003**：P0应按TMDB cast order保存前20名主要演员。
- **FR-CREDIT-004**：每名主要演员至少应包含TMDB Person ID、姓名、数据源存在时的原始姓名、角色名character和cast order。
- **FR-CREDIT-005**：系统应支持按演员搜索影片。
- **FR-CREDIT-006**：导演和演员都属于Person类型的影视人物，具体关系模型由数据库设计决定。
- **FR-CREDIT-007**：后续数据设计不得把导演姓名和演员列表仅保存为无法建立关系和检索的长字符串。

#### 11.3.5 Poster、Backdrop、评分和同步信息

- **FR-META-015**：Movie必须具备一个主要Poster的产品能力，中文环境优先选择适合中文展示的海报。
- **FR-META-016**：系统只保存Poster和Backdrop的图片定位信息，不在数据库中保存JPG或PNG二进制图片本体。
- **FR-META-017**：P0允许保存并展示TMDB vote_average和vote_count；缺失时允许为空。
- **FR-META-018**：TMDB评分必须明确标识为“TMDB评分”，不得与用户评分混淆。
- **FR-META-019**：P0没有用户为影片打1至10分的功能，不得自行增加user rating需求。
- **FR-META-020**：Movie必须能够表达元数据Provider、外部影片ID和最近一次成功同步元数据的时间；P0 Provider固定为TMDB，但Movie领域不得只能表达TMDB一种来源。
- **FR-META-021**：演员、导演、上映日期、标准时长、客观评分等事实不得由LLM生成。
- **FR-META-022**：Movie必须具备一个来自TMDB的主Backdrop产品能力，用于影片详情页的宽幅Hero视觉背景；TMDB没有可用Backdrop时允许为空。
- **FR-META-023**：主Poster与主Backdrop必须是两个独立展示图片概念；Poster用于海报墙、搜索结果、推荐卡片和列表，Backdrop用于影片详情页宽幅背景，不得互相替代为同一概念。
- **FR-META-024**：系统应将最终选定的主Poster和主Backdrop下载并长期保存到自有OSS，日常由Vue从自有OSS或其CDN加载；普通片库浏览不得以实时访问TMDB图片服务为前提，MySQL不保存图片二进制。
- **FR-META-025**：同一Movie在同一系统中只维护一套公共主Poster和主Backdrop，不提供用户级选图、图片锁定、多候选图库或不同用户不同海报。选图采用统一的系统级语言与回退规则，具体优先级可在后续详细设计中调整。
- **FR-META-026**：Movie应保留TMDB影片身份、元数据来源以及原始Poster/Backdrop来源定位，并保存系统持久化图片的稳定资源定位；具体数据库字段名称留给后续数据库设计。
- **FR-META-027**：普通扫描、登录和浏览不得自动替换已持久化的公共Movie图片。只有用户或未来管理员明确发起重新刮削、刷新元数据或重新同步影片时才允许更新；更新后所有关联该Movie的用户统一看到新图片。

#### 11.3.6 中文数据策略

- **FR-LOCALE-001**：展示层应优先使用TMDB中文本地化片名、中文简介和适合中文展示的主要海报，同时保留original title。
- **FR-LOCALE-002**：中文资料不存在时，系统应使用TMDB提供的其他可用语言内容降级，并明确其实际来源。
- **FR-LOCALE-003**：TMDB的language、region和fallback参数策略留给TMDB Provider详细设计确定。
- **FR-LOCALE-004**：若未来使用AI翻译，必须标识为AI生成或AI翻译，不得覆盖或冒充TMDB原始数据。

#### 11.3.7 P0明确不刮削的数据

P0不要求从TMDB取得或建立以下能力：

- 除单个主Backdrop外的完整Backdrop图库，以及Logo图库、演员头像墙和完整图片库。
- 制作公司、制片人、完整编剧体系、摄影、美术、作曲、全部Crew和全部Cast。
- 预算、票房、官方网站、社交媒体和获奖记录。
- 完整关键词体系、Trailer预告片、年龄分级和Certification。
- 完整Alternative Titles、Release Events完整列表和Collection完整业务体系。
- TMDB推荐电影接口和相似电影接口。

不得因为TMDB API提供某项数据就自动扩大P0保存范围。

### 11.4 个人片库

- **FR-LIB-001**：系统应提供电影海报墙或列表形式的片库主页。
- **FR-LIB-002**：系统应支持按片名、年份、类型、观看状态、收藏状态和来源进行浏览或筛选。
- **FR-LIB-003**：系统应展示最近添加、最近播放和当前不可用的影片或资源入口。
- **FR-LIB-004**：电影详情页应展示影片元数据、用户状态、可用媒体资源版本和AI助手入口，并可使用Movie的主Backdrop作为宽幅Hero视觉背景。
- **FR-LIB-005**：系统应区分逻辑影片和实际媒体资源，影片详情不得因为多个版本而重复显示为多部电影。
- **FR-LIB-006**：系统应明确展示影片当前是否至少存在一个可用媒体资源。
- **FR-LIB-007**：系统不应因外部元数据暂时不可用而阻止用户浏览已经建立的片库。
- **FR-LIB-008**：TMDB暂时不可访问时，已经存在的Movie仍应可查询，已经持久化到OSS的主Poster和主Backdrop仍应可展示；故障只影响新增电影、首次公共Movie建档或显式重新刮削/刷新。

### 11.5 多媒体资源版本

- **FR-VER-001**：同一逻辑影片必须能够关联一个或多个独立媒体资源版本。
- **FR-VER-002**：每个版本应展示来源、位置、可访问状态，以及探测成功时的实际时长、容器、分辨率、视频编码、bit depth、HDR、主要音轨编码、声道数和语言等文件事实。
- **FR-VER-003**：用户发起播放前应能明确选择媒体资源版本。
- **FR-VER-004**：系统可提供版本推荐顺序，但不得隐藏其他可用版本。
- **FR-VER-005**：AI推荐和Agent在用户未指定版本时，应基于当前用户可访问的WebDAV资源状态和可靠技术事实排序，并说明实际选用的版本；不得假设存在P0本地/NAS文件系统来源。
- **FR-VER-006**：某个版本不可用时，不应影响同一影片其他可用版本的播放。
- **FR-VER-007**：每个MediaResource必须能够表达一个可选Edition/Cut标签，例如Director's Cut、Extended Cut、Theatrical Cut、IMAX、Final Cut或Special Edition；无法可靠识别时允许为空。
- **FR-VER-008**：Edition属于MediaResource的资源版本语义，不属于Movie事实；同一影片的不同Cut必须继续关联同一个逻辑Movie，不得据此创建重复Movie。
- **FR-VER-009**：P0 Edition优先来自文件名或目录名中的明显标签并采用确定性解析；不得由ffprobe识别，不得由LLM猜测，也不得使用Movie级TMDB资料替代具体文件的Edition。
- **FR-VER-010**：P0只要求展示一个可选Edition标签，不建立独立Edition实体、标准化版本知识库或不同剪辑版剧情差异分析能力。

### 11.6 收藏、标签与观看状态

- **FR-PER-001**：用户应能收藏或取消收藏影片。
- **FR-PER-002**：用户应能将影片手动标记为未看、在看或已看。
- **FR-PER-003**：用户应能添加和移除个人标签。
- **FR-PER-004**：系统应区分TMDB Genre、用户标签和AI语义标签，避免混淆客观分类与模型推断。
- **FR-PER-005**：AI语义标签应标明为AI生成，并允许用户删除或纠正。
- **FR-PER-006**：收藏、标签和观看状态应可参与传统搜索、AI搜索和推荐。

### 11.7 传统搜索

- **FR-SEARCH-001**：系统应支持按中文片名、原始片名和别名进行关键词搜索。
- **FR-SEARCH-002**：系统应支持按导演、演员、Genre、年份、Movie标准时长、来源和观看状态进行组合筛选；MediaResource实际时长属于资源版本事实，不得与Movie时长混用。
- **FR-SEARCH-003**：传统搜索和自然语言搜索应并存，用户不应被迫使用AI完成精确查询。
- **FR-SEARCH-004**：搜索结果应明确显示影片是否拥有可用资源。

### 11.8 播放记录

- **FR-HIS-001**：用户成功发起一次外部播放器调用时，系统应记录播放启动行为。
- **FR-HIS-002**：播放记录至少包含影片、所选资源版本、播放来源和发起时间。
- **FR-HIS-003**：系统应维护影片最近播放时间和观看次数。
- **FR-HIS-004**：系统不得将“启动播放器”自动等同于“完整看完影片”。
- **FR-HIS-005**：用户可在播放后手动更新未看、在看或已看状态。
- **FR-HIS-006**：第一版不要求从mpv同步精确播放进度。

### 11.9 MediaResource媒体技术信息与探测

#### 11.9.1 P0探测来源

- **FR-PROBE-001**：P0必须增加MediaProbeProvider抽象，并以ffprobe作为唯一实际实现FfprobeMediaProbeProvider。
- **FR-PROBE-002**：媒体技术探测属于Spring Boot媒体资源基础设施能力，不属于FastAPI、LangChain、LangGraph或LLM职责。
- **FR-PROBE-003**：WebDAV来源直接提供文件名、相对路径、ResourceLocator、文件大小、文件修改时间、Provider/来源信息，以及来源支持时的稳定资源ID。
- **FR-PROBE-004**：ffprobe只负责分析实际媒体内容，不负责识别影片、生成Movie事实或建立TMDB关联。

#### 11.9.2 P0媒体技术字段

ffprobe在能力可靠且数据存在时应尝试取得：

1. MediaResource实际媒体时长duration。
2. 容器格式，例如Matroska/MKV或MP4。
3. 视频编码，例如HEVC、H.264或AV1。
4. 视频宽度。
5. 视频高度。
6. bit depth，例如8bit或10bit。
7. 可可靠判断的HDR类型，例如HDR10、HLG或Dolby Vision；不能可靠判断时为UNKNOWN或空。
8. 主要音轨编码，例如AAC、AC3、EAC3、DTS、DTS-HD或TrueHD。
9. 主要音轨声道数，例如2.0、5.1或7.1。
10. 主要音轨语言；媒体中不存在语言标记时允许为空。

- **FR-PROBE-005**：P0媒体探测用于版本展示、筛选和区分，不发展为MediaInfo完整克隆。
- **FR-PROBE-006**：系统不要求结构化保存每个视频流的全部FFmpeg字段、每条字幕的私有参数、GOP、Bitstream、逐帧信息、全部Metadata Tag或全部音轨高级参数。
- **FR-PROBE-007**：ffprobe完整原始JSON不得直接成为核心业务模型；少量非核心扩展信息是否保留为JSON留给数据库设计决定，核心展示和筛选信息必须可独立表达。
- **FR-PROBE-008**：bit depth和HDR等无法可靠取得的技术事实必须保持UNKNOWN或空，不得根据文件名或LLM猜测。

#### 11.9.3 WebDAV P0探测策略

- **FR-PROBE-009**：P0影片发现和TMDB识别只依赖WebDAV提供的文件名、大小、路径和资源定位，不得依赖ffprobe成功。
- **FR-PROBE-010**：WebDAV资源只在能够形成当前可访问的远程媒体定位且预计成本合理时执行best-effort ffprobe探测。
- **FR-PROBE-011**：WebDAV远程ffprobe失败、超时或被跳过时，不得阻止MediaResource入库、TMDB匹配、Movie创建或播放地址后续解析；对应技术字段允许UNKNOWN或空。
- **FR-PROBE-012**：系统不得为了ffprobe探测而要求完整下载远程电影。
- **FR-PROBE-013**：未来FileSystem或Local Agent接入后的本地探测策略不属于P0实现和验收范围。

#### 11.9.4 两种时长的强制区分

- **FR-DURATION-001**：Movie.runtime表示TMDB提供的标准影片时长，适用于影片级展示与选片筛选。
- **FR-DURATION-002**：MediaResource.duration表示ffprobe对某个实际文件探测得到的时长，适用于资源版本展示和比较。
- **FR-DURATION-003**：Movie.runtime与MediaResource.duration允许不同，不得建立相等约束或互相覆盖。
- **FR-DURATION-004**：剧场版、导演剪辑版、加长版、删减版和片头片尾差异都可能造成MediaResource.duration与Movie.runtime不同。

### 11.10 数据来源责任矩阵

| 数据类别 | 回答的问题 | P0权威来源 | 主要内容 | 明确禁止 |
| --- | --- | --- | --- | --- |
| Movie影片事实 | “这是什么电影？” | TMDB官方API | TMDB Movie ID、中文片名、原始片名、上映日期/年份、简介、runtime、原始语言、国家/地区、Genre、导演、前20名主要演员与角色、主Poster、主Backdrop、TMDB评分与人数、Provider和同步时间 | LLM生成或覆盖事实；ffprobe反推影片事实 |
| MediaResource文件事实与版本语义 | “我实际拥有的这个文件是什么？” | P0 WebDAV + 确定性命名解析 + best-effort ffprobe | 文件名、大小、相对路径、ResourceLocator、来源、修改时间、可选Edition标签，以及探测成功时的actual duration、容器、分辨率、视频编码、bit depth、HDR、主要音轨编码/声道/语言和文件状态 | 用TMDB替代文件Edition/技术参数；由ffprobe或LLM猜测Edition；把临时PlaybackLocator当稳定定位 |
| AI生成语义信息 | “这部电影给人的感觉是什么，是否符合当前需求？” | LLM基于TMDB事实和可靠RAG资料生成 | 情绪、节奏、氛围、观看场景、AI语义标签、一句话推荐、个性化理由、AI风格总结和内容解释 | 覆盖TMDB或MediaResource客观事实；伪装为官方资料 |

以下概念必须保持独立：

- TMDB Genre不等于AI语义标签。
- TMDB评分不等于用户评分；P0不存在用户评分功能。
- Movie的主Poster与主Backdrop是用途不同的图片定位信息，均不等于视频文件，数据库不保存图片二进制本体。
- Edition属于MediaResource；不同Edition不改变Movie身份，也不由ffprobe、TMDB或LLM推断。
- ResourceLocator不等于播放时临时产生的PlaybackLocator。
- Movie.runtime不等于MediaResource.duration。

### 11.11 轻量业务与审计记录

- **FR-OP-001**：系统应记录已建立可信用户身份后的关键业务操作，范围包括登录成功、媒体来源新增/修改/删除/启停/连接测试、扫描开始/完成/失败、人工确认或修正影片识别、AI请求/失败/降级及任务类型、播放请求和播放定位获取结果。登录失败等尚未建立可信CurrentUser的认证失败事件由脱敏的安全/技术日志记录，不自动创建用户OperationRecord。
- **FR-OP-002**：OperationRecord服务于关键业务行为和管理员状态变更的轻量追溯，不是通用技术日志数据库、企业审计中心、事件溯源系统或ELK类独立日志平台。
- **FR-OP-003**：OperationRecord概念上应能表达`actorUserId`、`actorRole`、`operationType`、`targetType`、`targetId`、`result`、`request_id`、适用时的`task_id`和`duration`、时间及脱敏摘要；具体字段与存储结构留给后续03数据库设计。
- **FR-OP-004**：操作记录不得保存密码、完整JWT、WebDAV密码或Token、TMDB Token、模型密钥、临时播放凭据、完整敏感URL、完整AI Prompt或完整私人对话。
- **FR-OP-005**：操作记录写入失败不得使已经成功的收藏、扫描、播放请求、AI请求或来源修改回滚。
- **FR-OP-006**：系统只能记录“已请求播放”或“播放定位获取成功/失败”，不能因浏览器发出`mpv://`就记录影片成功播放完毕。
- **FR-OP-007**：普通用户只能查看本人OperationRecord；`ADMIN`只能通过明确、受控的管理员审计用例查询系统范围内经过脱敏的OperationRecord。部署维护者不因运行环境职责自动获得应用内审计权限。
- **FR-OP-008**：管理员登录成功、禁用用户、启用用户及其他真正影响系统状态的管理员操作必须记录OperationRecord，并明确标识actor为`ADMIN`；不要求为每个普通管理GET写一条业务记录。
- **FR-OP-009**：OperationRecord、后台摘要和技术日志均应优先记录标识、状态、阶段、耗时、错误类别、关联ID和脱敏摘要，不得以“可观察”为由保存完整用户敏感正文。
- **FR-OP-010**：普通登录失败安全/技术日志可记录`request_id`、时间、认证结果、失败类别、脱敏用户名标识，以及后续安全设计允许时的IP和User-Agent摘要；绝不得记录密码，也不得把输入username当作可信User ID。

### 11.12 轻量系统管理中心

- **FR-ADMIN-001**：系统应设置应用内部`ADMIN`角色，并在同一个Vue Web应用中提供受保护的轻量系统管理区域；不新建第二套管理前端工程，也不建设内容运营后台。
- **FR-ADMIN-002**：所有管理员能力必须由Spring Security在Spring Boot后端校验`ADMIN`权限；前端路由隐藏不是安全边界，`USER`手工构造管理请求时必须得到403或等价拒绝结果。
- **FR-ADMIN-003**：系统概览应展示注册用户总数、今日/近7日新增用户、近7日活跃用户、MediaSource/MediaResource总量、用户片库关系或入库规模、扫描成功/失败、AI成功/失败/降级与可用时的平均耗时、近期异常摘要等聚合信息；趋势仅限用户新增、扫描和AI调用等简单展示，不扩展为商业BI。
- **FR-ADMIN-004**：“活跃用户”在需求层定义为统计周期内存在成功登录或有效业务操作的去重用户；具体SQL、字段和去重实现留给后续数据设计。
- **FR-ADMIN-005**：管理员应能查询普通用户，并查看用户ID、用户名、昵称、角色、账号状态、注册时间、可提供时的最近成功登录时间，以及媒体源数量、片库规模、操作次数、AI调用次数等聚合使用统计。
- **FR-ADMIN-006**：P0管理员只能启用或禁用普通用户账号，不删除用户、不查看密码或密码Hash、不修改用户收藏/观看记录/播放进度/片库内容、不操作MediaSource凭据、不冒充用户，也不任意授予`ADMIN`。
- **FR-ADMIN-007**：受保护请求除验证JWT外，还必须保证当前账号仍处于允许访问状态；不因账号禁用需求引入Redis Token黑名单，具体Token失效策略留给API与安全详细设计。
- **FR-ADMIN-008**：管理员任务监控应能查看系统范围内扫描/索引等任务的`task_id`、用户标识、任务类型、状态、开始/结束时间、耗时、发现/成功/失败数量、错误类别和降级状态，以回答“扫描或索引为何失败”，不得演变为用户影片内容管理。
- **FR-ADMIN-009**：管理员AI监控应展示AI任务类型、调用/成功/失败/降级次数、平均耗时、最近错误类别、非敏感Provider/模型标识和`request_id`；Provider可靠返回时可预留Token Usage统计，但费用统计不是P0必选功能。
- **FR-ADMIN-010**：管理员可通过单独受控入口查询系统范围内脱敏OperationRecord、管理员审计记录、任务与AI运行摘要及必要的近期异常摘要；P0日志中心不提供全部原始技术日志全文检索，也不引入ELK、Loki或Splunk等平台。
- **FR-ADMIN-011**：管理员系统状态应聚合展示Spring Boot、MySQL、FastAPI、Chat Model Provider、Embedding Provider、向量存储、TMDB Provider和ffprobe的正常、异常或降级状态。WebDAV仅可展示来源失败聚合，不得以管理员身份遍历私人来源或取得用户凭据/完整URL。
- **FR-ADMIN-012**：管理员系统配置摘要只读且脱敏，可展示TMDB、FastAPI、Chat/Embedding Provider和ffprobe是否配置/可用，以及运行环境的非敏感部分；不得在线查看或编辑API Key、WebDAV/数据库密码、内部服务密钥或JWT签名密钥，也不建设复杂动态配置中心。
- **FR-ADMIN-013**：管理员默认不得在管理端查看用户具体收藏、具体观影内容、完整观看历史、MediaSource密码/Token、完整文件路径、PlaybackLocator、完整AI Prompt、完整私人对话或完整RAG敏感上下文；只允许最小必要聚合统计和脱敏审计字段。
- **FR-ADMIN-014**：管理员跨用户查询只能存在于明确的Admin use case中，并通过其他模块公开Application/Query API取得最小数据；不得把普通业务接口改成接收任意`userId`，不得由FastAPI AI Tool Gateway、LLM或Agent调用管理员能力。
- **FR-ADMIN-015**：系统管理员属于产品权限角色，部署维护者属于运行环境角色；二者可以由同一人承担，但部署维护者不自动成为`ADMIN`，`ADMIN`也不因此获得服务器、数据库或原始日志文件的直接访问能力。
- **FR-ADMIN-016**：P0系统管理中心保持“弱后台、强个人端”，不建设影视内容审核、公共资源运营、复杂CRUD、企业级告警/APM、细粒度管理员权限或大型监控大盘。

## 12. AI功能需求

### 12.1 AI总体要求

P0只以四个方向作为核心AI创新与评价对象：自然语言智能检索、个性化可解释推荐、RAG影片助手和LangGraph智能选片Agent。AI语义标签是支撑检索与推荐的内部能力，不形成第五个独立产品方向。

- **AI-GEN-001**：AI能力必须以真实片库和业务事实为基础，不得仅凭模型记忆回答用户拥有的资源、观看状态或可播放状态。
- **AI-GEN-002**：业务事实发生冲突时，以Spring Boot业务系统提供的当前数据为准。
- **AI-GEN-003**：AI输出应区分TMDB影片事实、MediaResource文件事实、用户数据、AI推断和AI生成内容。
- **AI-GEN-004**：AI无法取得足够依据时，应明确说明信息不足，不得编造。
- **AI-GEN-005**：AI结果应尽量简洁、可操作，并提供进入影片详情或选择资源版本的入口。
- **AI-GEN-006**：大模型与Embedding模型供应商、部署方式及模型选择为【待后续系统设计阶段确定】。
- **AI-GEN-007**：LLM只能生成情绪、节奏、氛围、观看场景、语义标签、推荐理由、个性化简介和内容解释等AI信息，并必须明确标识AI生成。
- **AI-GEN-008**：LLM不得生成、修改或覆盖TMDB影片事实和MediaResource文件技术事实。

### 12.2 自然语言片库搜索

- **AI-SEARCH-001**：用户应能用中文自然语言描述类型、年份、时长、观看状态、人物、情绪、节奏、氛围和观看场景等要求。
- **AI-SEARCH-002**：系统应抽取可确定的结构化条件，并对无法用固定字段表达的条件执行必要的语义检索。
- **AI-SEARCH-003**：结果默认严格限制在用户个人片库中。
- **AI-SEARCH-004**：系统应排除不满足明确硬条件的候选，不得为了凑数忽略用户限制。
- **AI-SEARCH-005**：每个候选结果应说明其满足了哪些条件，并展示当前可用资源概况。
- **AI-SEARCH-006**：无匹配结果时应如实说明，并建议用户放宽具体条件；第一版不得自动切换为互联网影片推荐。
- **AI-SEARCH-007**：用户应能在上一轮结果基础上继续提出“更短一些”“排除已看”“优先本地”等调整要求。
- **AI-SEARCH-008**：用户未明确指定资源版本时，“两个小时以内”等影片时长条件默认使用Movie.runtime；只有明确询问文件版本实际时长时才使用MediaResource.duration。

### 12.3 AI片库推荐

- **AI-REC-001**：推荐第一原则是用户真实拥有且当前至少有一个可访问资源版本。
- **AI-REC-002**：推荐可结合用户明确需求、收藏、观看状态、观看历史摘要、偏好、影片元数据和AI语义标签。
- **AI-REC-003**：推荐不得把模型知道但用户片库中不存在的影片混入第一版主结果。
- **AI-REC-004**：推荐结果应控制在便于决策的少量候选，并为每个候选提供个性化理由。
- **AI-REC-005**：推荐理由不得虚构用户历史或影片属性。
- **AI-REC-006**：当满足条件的可访问影片不足时，应返回实际数量并解释原因。
- **AI-REC-007**：推荐不以实现Netflix级大规模协同过滤为目标。

### 12.4 AI影片助手

- **AI-ASST-001**：AI影片助手应绑定当前影片上下文，不作为与片库无关的通用聊天入口。
- **AI-ASST-002**：助手应支持无剧透简介、风格说明、观看前背景、演职员解释、系列关系和相似片库影片等问题。
- **AI-ASST-003**：助手默认处于无剧透模式。
- **AI-ASST-004**：用户询问结局、关键反转或完整剧情时，系统必须先获得用户对剧透的明确许可。
- **AI-ASST-005**：剧透许可只影响相应会话范围，其有效范围与状态管理方式为【待后续系统设计阶段确定】。
- **AI-ASST-006**：助手回答应基于当前检索到的资料；缺少可靠资料时应降低结论强度或拒绝断言。
- **AI-ASST-007**：AI生成的一句话推荐、个性化简介或观影提示必须标明为AI生成，不得覆盖TMDB简介。

### 12.5 AI语义标签

- **AI-TAG-001**：系统可根据可靠影片资料生成情绪、节奏、氛围、观看门槛和适用场景等语义标签。
- **AI-TAG-002**：AI标签不得被展示为TMDB提供的客观Genre。
- **AI-TAG-003**：AI标签应能参与语义检索和推荐。
- **AI-TAG-004**：用户应能查看、删除或纠正AI标签。

## 13. RAG需求

### 13.1 P0知识范围

第一版RAG优先使用以下内容：

- TMDB官方API提供的影片事实元数据。
- 影片简介。
- 演职员资料。
- AI语义标签。
- 用户个人片库信息。
- 用户观看历史摘要。
- 已存在且来源可靠的系列关联信息；P0不要求建立TMDB Collection完整业务体系。

字幕文本不属于P0必要知识源，作为P1扩展。

### 13.2 RAG行为要求

- **RAG-001**：系统应先检索与当前问题相关的资料，再让LLM基于检索结果生成回答。
- **RAG-002**：RAG只能访问当前登录用户有权查看的片库信息和个人数据。
- **RAG-003**：用户片库、观看状态、资源版本和可访问性应使用业务系统的当前数据，不得仅依赖可能过期的向量索引。
- **RAG-004**：检索上下文应与当前影片或当前查询相关，避免无关资料干扰回答。
- **RAG-005**：回答应提供可理解的依据说明，例如“来自影片元数据”“来自你的片库”“来自观看历史摘要”。具体引用展示形式为【待后续系统设计阶段确定】。
- **RAG-006**：检索资料不足、相互冲突或时效未知时，系统应显式提示不确定性。
- **RAG-007**：事实性资料更新后，相关AI检索结果应能够在合理时间内更新，具体索引同步机制为【待后续系统设计阶段确定】。
- **RAG-008**：删除或失去访问权限的数据不得继续出现在用户可见的RAG回答中。
- **RAG-009**：向量数据库产品、文本切分方式、Embedding模型和召回排序策略为【待后续系统设计阶段确定】。

### 13.3 RAG可靠性要求

- 结构化业务事实优先于模型推断。
- TMDB影片事实优先于AI生成标签。
- TMDB Genre、TMDB评分、Movie.runtime和MediaResource.duration等事实概念必须保持其来源属性，不能由AI语义内容替代。
- AI生成内容必须保留其生成属性。
- RAG回答不得大段输出可能受版权保护的原始材料。
- 未来字幕RAG仅服务于用户个人片库范围，不提供字幕公开传播能力。

## 14. Agent需求

### 14.1 Agent定位

Agent用于执行需要多个真实业务步骤的影音任务。第一版Agent以只读查询、资源检查和推荐为主，不承担无确认的数据修改任务。

### 14.2 P0核心Agent任务

第一版至少完整支持以下复合任务或等价任务：

> 帮我找三部片库里没看过、两个小时以内、不要太压抑的科幻片，并检查当前WebDAV资源是否可播放。

### 14.3 必须具备的执行能力

- **AGENT-001**：理解用户自然语言目标和硬性、软性条件。
- **AGENT-002**：查询当前用户的真实片库。
- **AGENT-003**：查询当前用户的观看历史和观看状态。
- **AGENT-004**：按Genre、Movie.runtime和观看状态等明确条件筛选；只有用户明确指定资源版本事实时才查询MediaResource.duration。
- **AGENT-005**：必要时调用语义检索判断情绪、节奏等模糊条件。
- **AGENT-006**：查询候选影片关联的媒体资源版本。
- **AGENT-007**：检查候选资源当前状态。
- **AGENT-008**：按用户条件、可访问性和来源优先级进行排序。
- **AGENT-009**：生成基于实际执行结果的推荐理由。
- **AGENT-010**：条件不足或工具失败时，不得跳过失败步骤并伪造成功结果。

### 14.4 Agent交互要求

- 用户应能看到Agent当前正在执行的主要任务阶段，避免长时间无反馈。
- Agent最终结果应说明使用了哪些条件、是否完成资源检查以及为何采用当前排序。
- 当可用结果不足指定数量时，Agent应返回实际结果并说明缺少原因。
- Agent不得将“模型推测可播放”当作资源状态检查结果。
- Agent执行应具有步骤和工具调用上限，避免无限循环；具体限制为【待后续系统设计阶段确定】。

### 14.5 Agent权限边界

- **AGENT-SAFE-001**：第一版Agent不得删除影片、媒体资源或来源。
- **AGENT-SAFE-002**：第一版Agent不得批量修改标签、观看状态或用户信息。
- **AGENT-SAFE-003**：第一版Agent不得更改登录凭据或外部服务配置。
- **AGENT-SAFE-004**：未来增加写操作时，必须在执行前向用户展示具体影响并取得明确确认。
- **AGENT-SAFE-005**：LangGraph工作流的节点划分、状态结构和工具协议为【待后续系统设计阶段确定】。

## 15. 播放需求

### 15.1 第一版正式播放链路

第一版必须采用以下正式链路：

> Vue页面点击“使用mpv播放” → 请求Spring Boot获得当前播放信息 → Spring Boot从媒体来源取得或确认当前有效播放URL/路径 → 前端生成或取得正确编码的`mpv://`链接 → 浏览器调用Windows自定义URL协议 → Windows本机启动mpv → mpv直接读取媒体资源 → 系统记录播放启动行为

服务端不得以直接启动用户Windows上的`mpv.exe`作为正式方案。

### 15.2 播放功能要求

- **PLAY-001**：mpv是第一版默认外部播放器。
- **PLAY-002**：用户应能在播放前查看并选择同一影片的媒体资源版本。
- **PLAY-003**：系统应在播放前获取或确认所选资源当前有效的播放地址。
- **PLAY-004**：WebDAV资源必须在播放时检查状态并解析当前PlaybackLocator，不得把历史临时URL作为MediaResource永久身份。
- **PLAY-005**：`mpv://`链接中的媒体地址和必要参数必须经过正确编码，避免查询参数、特殊字符或中文路径被错误解析。
- **PLAY-006**：播放定位应在其适用时限内使用；WebDAV认证方式、Header传递、URL编码、重定向与mpv兼容范围由WebDAV Playback Technical Spike确定，不预设永久直链、Basic Auth、账号密码入URL或AList签名URL。
- **PLAY-007**：浏览器首次调用外部协议时，系统应向用户说明可能出现浏览器确认提示。
- **PLAY-008**：本机未安装mpv或未注册协议时，系统应提供安装/注册说明和复制播放地址操作，不要求自动安装。
- **PLAY-009**：来源不可访问、资源不存在、认证失败、播放定位解析失败或临时定位失效时，系统应阻止无效播放并给出明确错误原因及重试入口。
- **PLAY-010**：调用外部协议后，系统只能确认“已发起播放”，不得在缺少播放器反馈时宣称“播放成功”或“已观看完成”。
- **PLAY-011**：平台不负责视频解码、音频解码、HDR渲染、字幕渲染、视频转码或播放器内核能力。
- **PLAY-012**：第一版不要求libmpv内嵌播放，也不要求开发桌面播放桥接客户端。
- **PLAY-013**：复制播放地址时应向用户提示地址可能具有临时性和敏感性。
- **PLAY-014**：解析播放定位前必须校验当前JWT用户对MediaSource和MediaResource的访问权；Vue只消费Spring Boot返回的受控PlaybackDescriptor。

### 15.3 未来本地资源播放扩展

本地硬盘和仅局域网可达NAS不属于第一版云部署P0播放链路。未来本地部署可由`FileSystemMediaSourceAdapter`直接访问，云部署可由Local Agent/本地助手连接；届时必须区分服务端可读、Agent可读和Windows客户端mpv可达，并另行设计安全的路径映射或播放联动。本节不得解释为P0实现、测试或演示要求。

### 15.4 浏览器与协议兼容性

第一版的目标播放客户端为已安装mpv并已注册`mpv://`协议的Windows环境。支持的浏览器范围、协议链接格式、URL长度边界和检测策略为【待后续系统设计阶段确定】，但最终方案必须覆盖主流现代浏览器中的首次确认、取消调用和无法唤起等情况。

## 16. 媒体来源需求

### 16.1 通用来源要求

- **SRC-COM-001**：用户应能添加、查看、修改、启用、停用和测试媒体来源。
- **SRC-COM-002**：来源配置应包含用户可理解的名称和扫描范围。
- **SRC-COM-003**：系统应展示来源最近连接状态、最近扫描时间和最近异常。
- **SRC-COM-004**：来源停用后不得参与新扫描、搜索可用性判断和播放地址获取，但已入库信息应保留。
- **SRC-COM-005**：系统不得把媒体文件复制或上传到平台自身存储中。
- **SRC-COM-006**：来源凭据不得在普通页面、日志或AI上下文中明文展示。

### 16.2 未来文件系统与Local Agent扩展

- **SRC-FUTURE-001**：统一`MediaSource`/`MediaSourceAdapter`抽象必须保留，以便未来增加FileSystem、SMB或其他来源。
- **SRC-FUTURE-002**：未来本地部署可通过`FileSystemMediaSourceAdapter`直接访问本地硬盘或宿主系统已挂载的NAS。
- **SRC-FUTURE-003**：未来云部署可通过Local Agent/本地助手连接用户本地硬盘和仅局域网可达NAS；Local Agent可承担本地扫描、ffprobe、目录监听和本机播放器联动。
- **SRC-FUTURE-004**：上述Adapter、Agent、路径安全、通信协议和播放器联动均不属于本科毕设第一版P0，不得据此新增当前实现、测试、验收或演示任务。

### 16.3 WebDAV来源

WebDAV是P0正式远程MediaSource协议。AList、NAS WebDAV或其他标准WebDAV服务都可作为Provider；系统核心只识别WebDAV，不直接对接迅雷、阿里云盘、夸克、百度网盘等厂商API。

- **SRC-WEBDAV-001**：用户应能配置一个可访问的WebDAV服务及授权目录范围，并执行连接验证。
- **SRC-WEBDAV-002**：系统应能区分文件与目录，浏览或扫描目录，发现视频文件，并在服务提供时取得文件名、相对路径、大小、修改时间和稳定ResourceLocator。
- **SRC-WEBDAV-003**：系统应能检查资源存在性和可访问状态；凭据失效、服务不可达、目录不存在或文件被删除时，应显示明确状态。
- **SRC-WEBDAV-004**：系统应保存稳定ResourceLocator，播放时再解析当前PlaybackLocator；不得把临时播放URL作为MediaResource永久身份。
- **SRC-WEBDAV-005**：WebDAV凭据必须由Spring Boot受控管理，不得交给Vue长期持有，也不得发送给FastAPI、LLM、向量存储或普通日志。
- **SRC-WEBDAV-006**：WebDAV扫描后的文件名解析、Edition/Cut提取、TMDB识别和人工确认必须依赖与来源无关的统一Movie流程，为未来其他Adapter复用；不得把WebDAV协议细节写入识别逻辑。
- **SRC-WEBDAV-007**：P0不承诺所有WebDAV服务器具有完全一致的认证或mpv播放行为；详细兼容范围由后续来源设计与播放Technical Spike锁定。

### 16.4 第一版来源边界

第一版P0只实现WebDAV来源及`WebDavMediaSourceAdapter`。AList、NAS WebDAV、Nextcloud等均为同层WebDAV Provider，不是独立MediaSource类型；P0也不实现`FileSystemMediaSourceAdapter`、SMB Adapter、Local Agent或厂商级网盘Adapter。统一媒体源抽象仍是P0架构边界，不因只有一个实际Adapter而删除。

## 17. 非功能需求

### 17.1 易用性

- 新用户应能从界面理解“来源、影片、资源版本、播放地址”之间的关系。
- 来源配置、扫描失败、识别失败、播放失败和AI失败均应提供用户可理解的提示。
- AI入口应嵌入搜索、推荐和影片详情等实际业务页面，不应只提供孤立聊天框。
- 危险或不可逆操作必须明显区分；第一版Agent不执行此类操作。
- 关键长时任务应展示状态和进度，避免用户重复提交。

### 17.2 可部署性

- Spring Boot业务服务和FastAPI AI服务应能够部署在Linux、NAS或服务器环境中。
- Web服务的部署不得依赖服务器拥有Windows桌面环境或安装mpv。
- 外部服务地址、模型和WebDAV来源配置应能够按部署环境调整。
- Docker具体配置、进程编排和部署拓扑为【待后续系统设计阶段确定】。

### 17.3 兼容性

- Web前端应支持主流现代桌面浏览器。
- 播放客户端第一版以Windows和mpv为目标环境。
- WebDAV目录与资源名称应正确处理中文、空格及常见特殊字符。
- WebDAV播放定位中的查询参数和特殊字符不得因协议调用而丢失；无法可靠传递时应降级为复制播放定位。

### 17.4 可靠性

- 单个来源、TMDB API、ffprobe或AI服务故障时，已入库的基础片库数据应尽可能继续可浏览。
- 扫描任务失败不得破坏已经确认的影片与资源关联。
- AI服务不可用时，传统搜索、片库浏览、收藏和手动播放入口不应整体失效。
- 重复操作应避免产生重复播放记录以外的异常业务数据；重复行为的判定规则为【待后续系统设计阶段确定】。

### 17.5 可维护性与可观察性

- **可追踪性**：Vue进入Spring Boot的关键请求应获得`request_id`，并在Spring Boot调用FastAPI时继续传递，使同一请求能够关联两侧结构化技术日志。
- **任务可追踪性**：扫描、索引等长任务应具有`task_id`，能够定位用户范围、处理阶段、结果数量、耗时、错误类别、降级状态和可重试性。
- **可审计性**：关键普通用户操作和影响系统状态的管理员操作应形成脱敏OperationRecord；普通用户仅查本人记录，`ADMIN`通过受控用例查询系统级脱敏记录。
- **可观察性**：系统应提供核心服务、外部依赖、近期错误、扫描/索引任务和AI调用的基础运行状态，不建设P0 APM或商业监控平台。
- **异常可定位性**：用户界面可显示简洁、可行动的错误，但内部结构化日志必须能够按模块、用例、`request_id`、`task_id`和依赖定位原因；系统异常可以在内部技术日志保留必要堆栈，绝不能直接返回前端。
- **日志分层**：A层为MySQL中的业务/审计OperationRecord，B层为Spring Boot与FastAPI的技术运行日志，C层为任务与AI调用可观察摘要；三者用途不同，不得把所有INFO日志写入MySQL。
- **结构化字段**：技术日志至少应在适用时表达`timestamp`、`level`、`service`、`module`、`request_id`、`task_id`、可信`user_id`、operation/use case、`duration`、`result`、`error_category`、`degraded`、`dependency`和`retryable`。
- **问题定位覆盖**：日志与运行摘要应能回答登录成功/失败、来源变更、扫描发起与失败阶段、单资源/TMDB/ffprobe错误、AI任务/FastAPI/LLM Provider错误与降级、跨服务请求链路、PlaybackLocator获取失败、管理员账号启停、外部依赖异常、可重试性和总体耗时等问题。
- **最小必要与脱敏**：日志、OperationRecord、管理后台和健康接口只记录标识、状态、阶段、耗时、错误类别、关联ID及脱敏摘要，不保存用户敏感正文或凭据。

### 17.6 可扩展性

- 后续应能够在不改变逻辑影片与资源版本核心关系的前提下扩展电视剧、其他标准来源协议和其他播放器。
- 架构应保留MovieMetadataProvider替换能力，但P0唯一实际影片数据源固定为TMDB；LLM、Embedding模型和向量存储仍不得在需求层绑定单一供应商。
- 扩展能力不得要求第一版提前实现对应功能。

### 17.7 可访问性与界面一致性

- 关键状态不得只依靠颜色表达，应同时使用文字或图标。
- 加载中、无数据、错误、不可访问和AI生成内容应具有一致且明确的视觉状态。
- 中文应作为第一版默认交互语言，影视原始标题应保留展示。

## 18. 性能需求

### 18.1 目标规模

第一版按个人片库规模设计，验收参考上限为：

- 逻辑电影数量不超过10,000部。
- 媒体资源版本数量不超过30,000个。
- 以单用户或少量家庭用户低并发使用为主。

该规模用于功能和性能验证，不代表商业级并发承诺。

### 18.2 页面与业务查询

- 在参考规模、服务正常且不依赖外部实时调用时，片库分页、详情、收藏和观看状态等常用操作的目标响应时间不超过2秒。
- 传统关键词搜索和结构化筛选的目标响应时间不超过2秒。
- 页面应采用分页或等效的渐进加载方式，不得一次性要求浏览器渲染全部片库。

### 18.3 扫描与刮削

- 用户启动扫描后，系统应在2秒内反馈任务已接受或明确失败原因。
- 系统应持续提供可见进度，不对跨网络扫描和外部刮削的总完成时间作固定承诺。
- 单个文件或单次外部查询失败不应导致整个扫描任务无结果终止。
- WebDAV远程ffprobe应具有严格的单资源超时、请求和成本边界，并且不得延迟整批资源完成入库。

### 18.4 AI响应

- 普通自然语言片库搜索在模型服务正常时，目标为15秒内返回完整结果或阶段性反馈。
- 影片助手普通问答在模型服务正常时，目标为15秒内返回结果或阶段性反馈。
- P0复合Agent任务在依赖服务正常时，目标为30秒内完成；超过该时间应持续展示明确执行状态，并允许用户终止等待。
- AI响应时间受外部模型和网络影响，超时时系统必须给出可重试提示，不得无限等待。

### 18.5 播放地址

- 用户发起播放后，系统应优先快速完成资源状态确认和当前地址获取。
- 若获取过程超过5秒，界面应展示正在获取或检查的状态。
- 系统不得为了缩短响应时间返回已知可能过期的WebDAV播放定位。

## 19. 安全与隐私需求

### 19.1 身份与访问

- 未登录用户不得访问片库、播放地址、来源配置、观看记录或AI上下文。
- 用户只能访问属于本人或明确授权给本人的个人数据。
- 登录状态过期后，系统应要求重新认证。
- 第一版正式认证方案为Spring Security + JWT；Vue使用`Authorization: Bearer <JWT>`访问Spring Boot，由Token解析、签名验证和过期校验建立可信CurrentUser。
- Spring Security对普通业务执行`USER`/`ADMIN`已认证校验和CurrentUser归属控制，对管理用例额外执行`ADMIN`角色校验；`USER`不得调用Admin Application Service。
- 新注册用户只能获得`USER`，`ADMIN`初始化不经过普通注册流程，具体安全方式留给后续详细设计。
- 已禁用账号的受保护请求即使携带签名有效且未过期的JWT也不得继续访问；P0不因此引入Redis Token黑名单。
- JWT只证明当前用户身份，不能替代MediaSource、MediaResource、个人状态、播放、AI和操作记录的对象归属校验。
- 浏览器用户JWT只用于Vue到Spring Boot；不得直接交给FastAPI作为业务授权。Spring Boot到FastAPI继续使用服务身份和短时限权AI上下文令牌。

### 19.2 来源凭据与播放地址

- WebDAV凭据、模型密钥和其他敏感配置必须受到保护，不得在前端普通页面、FastAPI、LLM、向量索引或日志中明文暴露。
- 如果某个WebDAV Provider产生带签名参数的临时URL，该URL可能包含访问能力，必须按敏感信息处理；这不是WebDAV协议的统一行为。
- 系统只应在用户明确发起播放时向对应客户端提供必要播放信息。
- 复制临时播放地址时应提示有效期和泄露风险。
- WebDAV远程ffprobe使用的短时播放定位只允许在Spring Boot媒体探测链路内短暂使用，不得进入日志、AI上下文、向量索引或长期数据库。

### 19.3 自定义协议安全

- 系统构造的`mpv://`调用只能用于经验证的媒体地址或路径，不得接受未经约束的任意本地命令。
- URL编码和参数处理必须避免媒体地址被解释为额外命令或非预期参数。
- P0不开发自定义协议处理程序；实际`mpv://`兼容格式、前端构造校验和浏览器边界由播放模块Technical Spike锁定。

### 19.4 AI数据隐私

- 发送给第三方模型的数据应遵循最小必要原则。
- 来源凭据、临时PlaybackLocator（包括某些Provider产生的签名URL）、密码和密钥不得进入LLM上下文。
- 用户应被告知AI可能使用片库信息、观看历史摘要和偏好生成回答。
- 用户应能清除个人AI会话或用于推荐的偏好数据；具体保留周期为【待后续系统设计阶段确定】。
- 模型供应商的数据处理策略应在系统设计和部署说明中明确。

### 19.5 媒体来源访问安全

- 系统只能扫描当前用户配置且有权访问的WebDAV目录范围。
- 第一版对影视文件以读取和管理信息为主，不得因扫描、识别或刮削修改、移动或删除原始视频文件。
- ResourceLocator、目录信息和资源存在性不得在无关用户之间泄露。

### 19.6 管理端与日志隐私边界

- “个人数据私有”表示产品业务权限严格隔离，不承诺数据库所有者或服务器所有者在物理层面绝对无法访问；产品设计仍必须默认不给管理员提供查看用户私人观影明细和AI私人内容的能力。
- 管理员页面、OperationRecord、技术日志、错误响应、Actuator/健康接口和配置摘要均不得泄露：明文密码、作为后台功能展示的password hash、完整JWT、Refresh Token、WebDAV密码/Token、TMDB Token、LLM/Embedding API Key、FastAPI内部服务密钥、完整敏感URL、临时PlaybackLocator、带签名的完整播放URL、完整AI Prompt、完整私人对话、完整RAG敏感上下文或未脱敏厂商请求/响应。
- 管理端返回脱敏DTO，不返回数据库DO、异常堆栈、用户凭据或原始技术日志文件。
- FastAPI AI Tool Gateway、LLM和Agent只服务当前普通用户范围的AI业务，不因调用者具有`ADMIN`角色而获得管理员级聚合查询、审计或账号管理能力。

## 21. 系统边界

### 21.1 系统负责

- 个人用户登录、偏好和观看数据。
- WebDAV来源配置和状态展示；AList等仅作为Provider。
- 电影资源扫描、识别和元数据刮削。
- 通过TMDB官方API取得P0影片事实，通过ffprobe best-effort取得P0媒体技术事实。
- 按统一规则选择TMDB主Poster/Backdrop，将图片长期保存到自有OSS，并在日常浏览中提供稳定图片来源。
- 逻辑影片与多个媒体资源版本管理。
- 片库浏览、搜索、收藏、标签和观看状态。
- 自然语言片库检索、片库内推荐和影片助手。
- RAG知识检索和Agent只读复合任务。
- 获取或确认当前播放地址并构造安全的mpv协议调用。
- 记录播放启动行为。
- 记录关键用户业务操作，并允许用户查看本人操作记录。
- 提供`USER/ADMIN`两级授权和同一Vue应用内的轻量系统管理中心。
- 允许`ADMIN`查看系统聚合指标、普通用户基础账号状态、任务/AI运行摘要、系统级脱敏OperationRecord、核心依赖健康和只读脱敏配置摘要，并启停普通用户账号。
- 为Spring Boot与FastAPI提供分离的结构化技术日志，并通过`request_id`和`task_id`支持基础排障。
- 为AI搜索、推荐、RAG和Agent完成论文实验及P0验收评价。

### 21.2 系统明确不负责

- 保存、上传、下载聚合或公开分发影视视频文件；将影片展示图片保存到OSS不等于保存或分发影视视频资源。
- 直接适配各网盘厂商，或提供公共影视资源搜索。
- 开发视频/音频解码、HDR渲染、字幕渲染、播放器内核或转码能力。
- 开发Electron、Qt、原生Windows、移动端或电视端客户端。
- 服务端直接启动用户Windows上的mpv进程。
- libmpv内嵌播放。
- 第一版完整电视剧、季、集管理。
- 第一版PotPlayer支持。
- 第一版精确播放进度同步和字幕RAG。
- Netflix级推荐算法或基于海量用户的协同过滤。
- 商业会员、付费、广告、CDN和版权运营。
- 企业级租户体系、组织部门、permission表级权限、复杂RBAC、多级管理员或菜单权限树；P0仅保留`USER/ADMIN`两级角色和轻量系统管理。
- 影视内容审核、内容运营、公共资源管理、管理员代用户维护个人片库或大型商业运营后台。
- 管理员查看/修改用户私人观影明细、MediaSource凭据、完整文件路径、PlaybackLocator或完整AI私人内容。
- P0集中式技术日志平台、全量日志Web检索、APM平台、Prometheus/Grafana强依赖或复杂告警中心。
- Agent在未经用户确认的情况下执行写入、删除或批量修改。
- 抓取影视网页HTML、自建影视数据爬虫或让LLM替代TMDB。
- P0同时接入IMDb、豆瓣、OMDb、TVDB或多个影片元数据Provider。
- 将ffprobe建设为独立微服务或要求远程影片完整下载后才能入库。
- 用户影片评分功能。

### 21.3 数据所有权边界

实际视频文件始终保留在用户WebDAV来源背后的NAS、网盘或远程存储中。AList仅可能是其中一个WebDAV Provider。平台不提供公共可播放影视资源，只保存为实现当前用户片库管理、用户行为和AI检索所必要的信息、索引及已选定的影片展示图片，不取得或改变影视文件所有权。共享公共Movie元数据与OSS展示图片不构成用户资源所有权；用户仍须拥有本人可访问的MediaResource才能在个人片库中看到和播放对应Movie。

普通用户对MediaSource、MediaResource可见范围、收藏、用户标签、观看状态、播放历史、推荐偏好、AI搜索/RAG范围、AI会话和本人OperationRecord享有严格的业务权限隔离。管理员默认只取得完成账号状态管理、聚合统计、运行监控和脱敏审计所需的最小信息，不取得用户私人内容维护权。这里的“私有”是产品业务授权边界，不代表数据库所有者在物理层面绝对无法访问；部署与数据治理仍须遵守最小权限、备份和日志脱敏要求。

## 22. 异常场景

| 异常场景 | 系统预期表现 |
| --- | --- |
| 来源无法连接 | 显示来源不可用和可理解原因，允许重新测试，不影响其他来源 |
| WebDAV扫描目录不存在 | 停止该范围扫描，保留历史数据并标记相关资源状态 |
| 单个文件读取失败 | 记录失败项并继续处理其他文件 |
| 影片无法识别 | 进入待确认列表，不由LLM编造元数据 |
| 多个影片候选冲突 | 展示候选并要求用户选择 |
| TMDB API不可用、限流或超时 | 保留MediaResource、已有Movie资料及OSS中的主Poster/Backdrop；已有片库正常浏览，新资源进入待刮削/未识别状态并允许稍后重试，显式刷新暂不可用 |
| WebDAV ffprobe失败或成本过高 | 跳过媒体探测，不阻止TMDB识别、Movie关联或后续播放定位解析 |
| TMDB中文资料缺失 | 使用TMDB其他可用语言内容降级，不让LLM翻译后冒充TMDB数据 |
| 同一影片发现新版本 | 关联为新的资源版本，不重复创建逻辑影片 |
| 资源文件被删除 | 标记资源不可访问，不静默删除用户历史 |
| WebDAV凭据失效 | 标记来源认证失败并提示用户修正配置 |
| WebDAV来源不可达或播放定位失效 | 播放前重新检查并解析；仍失败则提示、允许重试或复制播放定位 |
| mpv未安装或协议未注册 | 提供安装/注册说明和复制地址操作 |
| 浏览器取消外部协议调用 | 不宣称播放成功，保留再次发起入口 |
| 浏览器不支持或阻止协议 | 提供兼容性说明和复制地址操作 |
| 播放地址包含中文或特殊字符 | 正确编码；编码失败时不得发起可能错误的调用 |
| LLM不可用或超时 | 说明AI服务暂不可用，保留传统搜索和片库操作 |
| 向量检索无结果 | 使用可用结构化条件或说明资料不足，不编造结果 |
| AI推荐候选不足 | 返回实际数量并说明哪些条件导致不足 |
| Agent某一步工具失败 | 显示失败阶段，不将未检查资源声明为可用 |
| 用户提出Agent写操作 | 第一版拒绝自主执行，并说明当前仅支持只读任务 |
| 用户直接询问结局 | 在未获明确许可前保持无剧透并提示切换 |
| 用户会话失效 | 中止敏感操作并要求重新登录 |
| 用户尝试访问他人对象标识 | 拒绝访问且不泄露对象敏感信息，必要时记录脱敏失败操作 |
| USER尝试访问管理能力 | 返回403或等价拒绝，不因前端路由可见性改变后端授权结果 |
| 普通用户账号被ADMIN禁用 | 后续受保护请求校验账号状态并拒绝访问；不依赖Redis Token黑名单 |
| ADMIN禁用或启用普通用户 | 完成明确状态变更并形成标明ADMIN actor、目标和结果的脱敏OperationRecord |
| FastAPI不可用 | Java核心管理页面仍可访问，AI状态显示不可用或降级，不拖垮整个管理中心 |
| MySQL或其他核心依赖异常 | 健康状态反映异常或降级；界面不返回内部堆栈、密钥或敏感配置 |
| 操作记录写入失败 | 保留已完成主业务结果，记录技术错误并允许后续补偿，不引入消息队列 |

## 23. 验收标准

### 23.1 P0端到端验收

使用两个彼此独立的测试用户和各自WebDAV测试电影目录，完成以下验收：

1. 用户能够自主注册并以JWT Bearer登录；新用户首次进入时没有MediaSource、MediaResource、个人片库关系、其他用户资源或平台赠送的可播放影片。数据库中已有公共Movie元数据不会自动进入其片库。
2. 用户能够添加自己的一个WebDAV来源并看到连接测试结果；AList如参与验收，只作为WebDAV Provider。
3. 系统能够扫描当前用户的WebDAV来源，展示进度、成功、待确认和失败项。
4. 系统能够通过确定性文件名解析和TMDB官方API识别电影，并取得中文优先的P0元数据。
5. 低置信度或错误匹配能够由用户确认或修正。
6. 同一电影的多个WebDAV资源和不同Edition/Cut能够归入同一逻辑影片，并作为独立MediaResource展示。
7. 用户能够浏览详情、传统搜索、收藏、添加标签并标记未看/在看/已看。
8. 用户能够通过中文自然语言检索真实片库，结果满足硬条件并给出匹配说明。
9. AI能够基于真实片库和观看历史摘要推荐当前可访问影片，不混入片库外电影。
10. 影片详情页助手能够在默认无剧透模式下回答，并在涉及结局前取得明确许可。
11. P0 Agent能够完成条件理解、片库查询、历史查询、必要的语义检索、版本查询、状态检查、排序和理由生成。
12. 用户能够选择媒体资源版本，并在播放时取得当前WebDAV PlaybackLocator。
13. 浏览器能够通过`mpv://`调用已正确安装和注册的Windows本机mpv。
14. 系统能够记录播放启动、最近播放时间、所选版本和观看次数，但不误判为完整看完。
15. mpv未安装、协议未注册、地址失效或来源不可用时，系统能够提供对应错误提示和复制播放地址等替代操作。
16. 用户A不能访问、扫描或播放用户B的来源和资源，AI也不能查询用户B片库；Movie仍可作为共享影片事实复用。
17. 系统能够按要求形成脱敏的关键用户操作记录，且记录失败不会回滚成功的主业务。

上述任一关键步骤无法完成且没有符合需求的降级说明时，P0闭环不视为通过。

### 23.2 AI搜索验收

使用预先准备的测试片库和查询集验证：

- 明确类型、时长、年份、观看状态、资源条件和MediaSource类型能够被正确执行。
- “轻松、压抑、节奏快、适合家庭”等语义条件能够得到有依据的匹配解释。
- 搜索结果只来自当前用户片库。
- 不满足硬条件的影片不会为了凑数进入结果。
- 无结果时不虚构影片，并能指出可放宽条件。
- 硬条件与语义条件分别处理，LLM不能擅自放宽硬条件；4K/HDR等条件只有在存在可靠资源事实时才能判定。

测试查询集、正确性评分方法和通过阈值为【待后续AI模块设计阶段确定】。

### 23.3 AI推荐验收

- 推荐结果必须来自当前用户真实拥有且有权访问的个人片库，不为凑数加入片库外影片。
- 已看排除、用户显式条件和资源可访问性逻辑必须正确；不可访问资源不得作为正常可看推荐。
- 推荐理由只能使用真实Movie事实、用户状态、可靠资源事实和明确标识的AI语义信息，不虚构用户历史或影片属性。
- 候选不足时返回实际数量并说明原因。
- 可使用适量人工评价验证推荐相关性与理由合理性；测试集、评分方法和通过阈值由后续AI详细设计确定，不建设商业级推荐评测体系。

### 23.4 RAG验收

- 回答能够使用当前影片和当前用户片库的相关资料。
- 观看状态和资源可访问性与业务系统当前数据一致。
- 缺少资料时明确说明不足。
- AI生成说明与TMDB影片事实、MediaResource文件事实能够被区分。
- 用户无权访问或已经删除的数据不出现在回答中。
- 回答默认无剧透，只有用户明确许可后才进入剧透模式。

### 23.5 Agent验收

对核心复合任务进行演示时，系统必须可证明地完成以下阶段：

1. 解析用户条件。
2. 查询真实片库。
3. 查询观看状态。
4. 执行明确条件筛选。
5. 对“不要太压抑”等条件进行必要的语义检索。
6. 查询媒体资源版本。
7. 检查资源状态。
8. 按当前用户可访问性、明确条件和可靠资源事实排序WebDAV版本。
9. 输出实际结果和理由。

仅由LLM直接生成一段推荐文本不视为Agent验收通过。

还必须覆盖无结果、不足指定数量、部分资源状态检查失败、工具失败、FastAPI降级和Agent步骤限制；任何分支都不得由LLM补充片库外电影。

### 23.6 播放验收

- WebDAV播放定位在点击播放时解析，不能使用已知过期或不可访问的历史定位。
- 当目标Provider产生签名参数时，相关参数以及中文或特殊字符能够被正确传递，或按既定规则降级为复制播放定位。
- 已安装并注册协议的Windows环境能够唤起本机mpv。
- 系统不会在浏览器仅发起协议后宣称播放器已成功播放完整影片。
- 未配置播放环境时有明确提示和复制地址能力。
- 不要求服务端安装或启动mpv。

### 23.7 非功能验收

- 在第18.1节参考规模下，常用片库和传统搜索操作达到目标响应时间。
- AI、TMDB或ffprobe不可用时，已入库的基础片库仍可浏览和搜索。
- 用户界面和日志不泄露来源密码、模型密钥、完整敏感URL或某些Provider产生的临时签名URL。
- 长时扫描和Agent任务具有可见状态，不出现无限等待且无提示的情况。
- LLM、Embedding、向量存储或FastAPI不可用时，非AI核心影音业务仍然可用。
- AI搜索、推荐、RAG和Agent的论文实验数据必须来自真实AI实现；Mock只用于开发联调和契约测试。

### 23.8 TMDB刮削与媒体探测验收

- 测试文件名同时包含Director's Cut、Extended Cut、IMAX等Edition标签与分辨率、编码、音频、发行组、Remux、HDR等噪声时，系统能够先保留Edition语义，再提取可用片名和年份候选。
- 系统能够完成TMDB搜索，并分别演示高置信度自动确认、低置信度人工确认和无候选保留未识别资源。
- 确认TMDB Movie ID后，系统能够取得中文片名、原始片名、上映日期/年份、简介、runtime、原始语言、多个国家/地区、多个Genre、主Poster、一个主Backdrop、导演、前20名主要演员、角色、cast order，以及可用时的TMDB评分和评分人数。
- 影片详情将评分明确标识为TMDB评分，不出现P0用户评分入口。
- Director和主要Cast能够参与搜索；人员关系不能只表现为一个不可检索的长字符串。
- WebDAV测试资源可在成本预算内通过ffprobe best-effort尝试取得实际duration、容器、视频编码、宽高、bit depth、HDR和主要音轨信息。
- WebDAV远程ffprobe失败、超时或被跳过时，MediaResource仍能入库并完成TMDB识别，技术字段允许UNKNOWN或空。
- Movie.runtime与MediaResource.duration能够同时表达不同值，彼此不覆盖。
- Genre与AI语义标签、TMDB事实与AI生成说明在展示和AI依据中保持明确区分。
- 同一Movie的不同Cut能够以不同MediaResource及其可选Edition标签展示，不创建重复Movie；无明确标签时Edition保持为空。
- 影片详情页能够使用一个主Backdrop作为Hero背景；Poster与Backdrop在海报墙/卡片和详情页宽幅背景中的用途保持区分，且不扩展为Backdrop图库。
- 同一公共Movie被两个用户的不同MediaResource关联时，两名用户看到同一套主Poster/主Backdrop；第二次命中不得重复取得完整TMDB资料或重复保存相同图片。
- TMDB暂时不可用时，已有Movie仍可查询，已保存到OSS的主Poster与主Backdrop仍可展示；Vue日常浏览不直接依赖`image.tmdb.org`。

### 23.9 轻量系统管理与可观察性验收

1. `USER`访问任何管理员接口均被Spring Security拒绝；仅隐藏Vue路由不视为通过。
2. `ADMIN`能够登录并进入同一Vue应用中的轻量管理区域。
3. `ADMIN`能够查看注册用户总数、近7日活跃用户等聚合指标，并查看普通用户基础账号信息和聚合使用统计。
4. `ADMIN`能够禁用和重新启用普通用户；禁用后该用户携带原有JWT访问受保护请求仍被拒绝。
5. 账号启停形成标明`ADMIN` actor、目标、结果、时间和`request_id`的脱敏OperationRecord。
6. `ADMIN`能够按受控用例查看系统级脱敏OperationRecord；普通用户仍只能查看本人记录。
7. 管理员页面和响应中不存在密码/password hash、API Key、WebDAV凭据、内部服务密钥、完整路径、临时PlaybackLocator、完整AI Prompt、完整私人对话或完整RAG上下文。
8. `ADMIN`不能通过管理端修改用户收藏、观看记录、播放进度、片库内容、MediaSource凭据或任意授予`ADMIN`，也不能冒充用户。
9. 管理员任务监控能够通过`task_id`定位扫描/索引任务的阶段、数量、耗时、错误类别和降级状态。
10. 管理员AI监控能够展示任务类型、成功/失败/降级、耗时、非敏感Provider/模型标识和`request_id`，且不保存或展示完整用户输入与上下文。
11. `request_id`能够关联一次Vue → Spring Boot → FastAPI调用两侧的技术日志；`task_id`能够定位一次扫描任务。
12. FastAPI/模型服务不可用时，管理员仍能查看Java核心系统状态，AI状态显示不可用或降级；非AI管理能力不被拖垮。
13. MySQL或关键依赖异常时，健康状态能够反映异常，并保持错误响应脱敏。
14. FastAPI AI Tool Gateway、LLM和Agent不能调用管理员能力。
15. 两个普通测试用户的MediaSource、MediaResource范围、个人状态、历史、AI/RAG数据和会话隔离不因`admin`模块加入而破坏。
16. Spring Boot/FastAPI技术日志、OperationRecord、后台页面和健康/配置摘要中均不存在敏感凭据泄露。
17. P0验收不要求Redis、Kafka、RabbitMQ、ELK/Loki/Splunk、Prometheus/Grafana或独立任务平台。

## 24. 第一版最终演示流程

毕业设计最终演示应按以下连续流程进行，避免只展示相互孤立的功能页面：

1. 用户自主注册并使用JWT Bearer登录Web系统，展示新用户默认空片库。
2. 添加一个属于当前用户的WebDAV来源并完成连接测试；如使用AList，仅说明其为WebDAV Provider。
3. 启动扫描，展示系统发现电影文件和处理进度。
4. 展示确定性文件名解析先保留Edition标签、再清理命名噪声并完成TMDB自动识别、中文优先元数据刮削以及一次低置信度人工修正。
5. 展示WebDAV远程ffprobe的best-effort结果或UNKNOWN/空降级，并展示探测失败不阻塞入库/TMDB刮削以及Movie.runtime与MediaResource.duration属于不同事实。
6. 进入个人片库，展示中文海报墙、影片详情页主Backdrop、TMDB事实资料、Genre、导演与演员搜索。
7. 展示同一逻辑影片关联多个WebDAV来源/目录及不同Edition/Cut的多个媒体资源版本。
8. 收藏一部影片并设置未看/在看/已看状态。
9. 输入自然语言查询：“找一部片库里没看过、两个小时以内、不太压抑的科幻片。”
10. 展示AI从真实片库返回结果、匹配条件、依据和资源概况。
11. 进入某部影片详情，使用默认无剧透AI助手了解影片风格和观看背景。
12. 提出涉及结局的问题，展示系统先取得剧透许可再回答。
13. 执行P0复合Agent任务，展示其查询片库、观看历史、语义条件、版本和资源状态的主要阶段。
14. 从Agent或影片详情结果中选择具体资源版本。
15. 播放WebDAV版本时，展示系统检查资源并解析当前PlaybackLocator。
16. 浏览器通过`mpv://`唤起Windows本机mpv并播放资源。
17. 返回系统，展示新增的播放启动记录、最近播放时间和观看次数。
18. 使用第二个用户展示默认空片库、来源/资源/个人状态/历史/AI会话不可跨用户访问和防IDOR，再展示本人操作记录；可选展示协议未注册、WebDAV来源不可用或远程探测失败时的降级处理。
19. 在个人影音主流程完成后，以`ADMIN`登录轻量管理中心，简要展示用户总数/活跃统计、最近扫描任务、AI调用统计、一条脱敏OperationRecord和核心依赖健康状态，并验证管理页面不出现用户敏感载荷。
20. 展示AI搜索、推荐、RAG和Agent的论文实验评价结果或验收记录。

管理员展示仅用于证明基础维护与可观察能力，不得替代或压过前述个人片库、AI选片和mpv播放主流程。

## 25. 留待后续系统设计阶段确定的事项汇总

以下事项不会改变本需求基线，但需要在后续设计中作出具体选择：

1. 用户注册字段校验、重复账号处理、`ADMIN`安全初始化方式，以及JWT过期/Refresh和账号禁用后现有Token的具体失效策略；开放自主注册、注册用户仅获`USER`、登录后默认空片库、受保护请求复核账号状态和Spring Security + JWT Bearer方案本身已经确定，P0不引入Redis Token黑名单。
2. TMDB API凭据、language/region/fallback、请求配额、字段映射，以及系统级主Poster/主Backdrop选择规则的具体优先级；TMDB来源、OSS长期持久化、每个Movie一套公共图片和普通访问不自动换图已经确定。
3. LLM、Embedding模型及其云端或本地部署方式。
4. 向量数据库、文本切分、索引同步和召回排序策略。
5. Spring Boot与FastAPI之间的受控业务调用形式。
6. 已验证mpv兼容href的实际格式、URL编码、安全校验、浏览器兼容和长度边界；由播放模块Technical Spike锁定。
7. WebDAV详细认证兼容范围、超时、重定向、服务差异及敏感配置保护载体；AList只作为测试或演示Provider之一。
8. 资源状态检查的具体策略和可用判定标准。
9. AI引用依据的界面展示形式。
10. 剧透许可的会话范围与状态管理。
11. LangGraph工作流、Agent工具协议、步骤上限、超时和重试策略。
12. AI会话与个人偏好数据的保留周期和清除机制。
13. 扫描、TMDB刮削、ffprobe探测和AI任务的任务调度与状态管理方式。
14. Docker部署、服务编排、运行参数、Spring Boot/FastAPI结构化日志输出与轮转方式、轻量健康检查聚合和部署维护者原始日志访问方案。

20. 管理员认证/授权、系统概览、用户基础管理、任务监控、AI监控、脱敏OperationRecord审计、系统健康和只读配置摘要的API详细设计；本需求文档不锁定最终URL。
